# 模块架构文档编写

## 职责与边界

本技能解释当前业务模块、平台模块或技术子系统的架构、运行方式与风险，不规划未落地方案，不代替整个项目的接手分析或单项业务闭环分析。

本文维护执行流程和交付检查；[模块发现规则](references/module-discovery.md) 维护模块划分与输出路径，[输出契约](references/output-contract.md) 维护参考结构与最低内容，[内容适配模型](references/architecture-doc-model.md) 维护条件内容，[证据与质量门禁](references/evidence-and-quality.md) 维护证据状态、读者复核与质量要求。

## 输入与前置条件

确定目标项目、模块范围、用户指定成果及操作类型，读取适用项目规范和现有文档。首次生成或整体重构完整读取输出契约；局部更新读取受影响要求，保留其他有效信息。事实源及模块发现入口按下列流程定位。

已有同模块文档优先原位维护；多个候选无法确定时先明确对象，不将目录名自动当作模块边界。缺少证据或访问能力时记录检查范围和缺口，不将未知当作不适用。

## 执行流程

仅保存已有成果时，核对所指基线、有效修正和输出位置后保存，不重新开展模块扫描或补写全文；报告原有证据状态和必要缺口。局部更新只对受影响模块、事实与引用执行适用步骤；首次生成或整体重构执行以下流程。

1. 发现模块和事实源。
   - 读取 `README.md`、`AGENTS.md`、已有架构/设计/API/需求文档、主要源码目录、路由、服务、存储、前端页面、测试和配置。
   - 运行 `scripts/detect_architecture_modules.py <repo-root>` 收集候选模块、现有架构文档、API/服务/前端/测试入口。
   - 输出目录和文件名按 [模块发现规则](references/module-discovery.md#输出路径) 确定。

2. 选择模块边界。
   - 读取 [模块发现规则](references/module-discovery.md)。
   - 按业务闭环、用户入口、API/CLI 边界、数据所有权、平台能力或技术子系统划分模块。
   - 不把每个文件夹机械生成成一篇文档；也不把多个职责强行塞进一篇大文档。

3. 确定文档结构。
   - 读取 [输出契约](references/output-contract.md)，按适用最低内容，以能力和运行链路组织局部依据、机制、风险与复核，共享内容集中维护。
   - 读取 [内容适配模型](references/architecture-doc-model.md)，按项目类型适配内容与结构。

4. 验证事实。
   - 读取 [证据与质量门禁](references/evidence-and-quality.md)。
   - 文档中的路径、API、命令、表名、配置项、页面入口和测试名称必须回查确认。
   - 不确定的内容不要写成事实；需要用户决策时先给推荐方案和依据。

5. 落地与索引。
   - 一项模块一篇文档，文件名使用稳定 kebab-case：`<output-dir>/<module-slug>.md`。
   - 有现有文档时优先更新原文件，不重复创建相同模块文档。
   - 按“验证与完成标准”逐篇检查内容和结构。
   - 同步需要的文档入口，例如 README 的文档索引或架构目录索引；不要复制全文。
   - 汇报写入文件的绝对路径、覆盖模块、证据来源和未覆盖风险。

## 核心约束

按模块生成当前事实架构文档，不写愿景文档、历史流水或未落地方案。每个结论必须能在代码、配置、路由、数据结构、测试或权威文档中找到依据。

除命令、代码、文件名、机器字段和目标仓库已有英文约定外，默认使用简体中文；用户明确要求英文时再改用英文。

候选扫描脚本只辅助发现，不能替代代码阅读。事实、推断和验证状态按证据契约区分；实际执行、静态确认和待确认不得混写。架构说明描述当前实现，发现实现与有效规范不一致时如实记录差异，不将违规实现提升为应遵守的规则。

## 产出边界与交付

产物采用输出契约的**参考结构**，不是技能正文的六章模板。按模块发现规则确定目录，每个模块一篇 `<output-dir>/<module-slug>.md`；已有同模块文档沿用原路径。同步受本次变更影响的 README、AGENTS 或架构索引入口，不复制模块全文。

文档边界遵循 [全局规范](~/ai-agent-config/config/force/document-boundaries.md)。首次生成或获准补全时，将下列分工落实为产物的具体边界说明，已有同等说明时复用。仅保存、逐字保存或局部更新保留授权基线，不为补边界扩写或重排，范围外缺口在交付中报告。

- 架构文档：解释当前模块如何工作、由哪些代码和数据支撑、如何使用、有哪些风险。
- README：保留项目概览、最小运行与使用路径及文档索引，不承载每个模块全部细节。
- AGENTS.md：AI 协作约束，只引用稳定架构入口，不复制模块说明。
- 需求/计划/开发留痕：记录目标、计划和过程；架构文档只沉淀当前已成立事实。

交付文件绝对路径、覆盖模块、证据来源、验证结果及未覆盖风险；不因发现架构风险自动修改生产实现或部署环境。

## 验证与完成标准

- 对每个输出文件运行 `scripts/validate_architecture_doc_structure.py <document-path> --custom-structure`；默认使用 `--custom-structure` 检查通用结构，只有项目或用户明确采用脚本内置骨架时才省略该参数。外部固定契约另行逐项核对；脚本通过不能替代最低内容的语义复核。
- 按证据与质量门禁回查路径、API、命令、表名、配置、页面入口、测试及依赖方向，检查链接、锚点、表格和 Mermaid；不能只列源码索引而不解释机制。
- 首次生成或获准补全时，沿代表性请求、业务流程或运维操作核对入口、处理、数据/状态结果和失败排查位置；多模块文档逐篇满足适用最低内容，不以总索引代替。
- 局部更新复核受影响内容，仅保存时核对原基线与确认状态；发现范围外缺口只报告。结构校验失败或运行验证未完成时分别说明，不宣称完整验收通过。
