# 开发计划与实施

## 职责与边界

参考：[编码规范](~/ai-agent-config/config/force/coding-standards.md) · [测试规范](~/ai-agent-config/config/force/testing-standards.md)。

计划维护已确认需求的技术方案、任务、依赖、验证安排与进度；业务规则引用上游，任务记录保留必要实际结果和证据入口，完整实施证据由已有实施记录维护，长期事实归架构文档。不因编写计划自动创建留痕或执行开发。

执行前读取 [需求协作共用契约](~/ai-agent-config/config/force/requirement/requirement-collaboration.md)，应用调研、继承、确认和阶段交接要求及其通用规范入口。

- 仅请求计划时交付计划；用户要求开发、修复、重构或生成后实施时，组织计划后继续已授权工作，无须再次取得“开始开发”确认。纯问答、只审查、仅编写需求/原型或未授权实施的讨论，不自动转入开发。
- 用户要求计划文档或项目规范要求时保存，默认文件名 `plan.md`；明确只要对话方案时不落盘。完整计划使用固定模板，开发中自动调用可用会话任务清单，保留目标、操作、结果和验证，不额外创建阶段性文档。

## 输入与前置条件

生成或实质调整代码实现方案时，读取编码规范；安排或调整验证时，读取测试规范。已读取的直接复用。

### 普通模式与专业模式

未指定模式时默认普通模式；同一计划后续更新继承已选模式，用户要求时切换。不能因为已有 PRD、需求复杂或风险较高就自动切换专业模式。两种模式共用任务粒度、验收、状态与风险要求，仅输入前置和原型准备方式不同；在计划来源处注明模式与依据。

| 模式 | 输入与推进规则 |
| --- | --- |
| 普通模式（默认） | 自然语言、会话结论、功能说明或技术目标均可直接生成计划；有相关文档就继承，不强制先生成闭环文档或 PRD。把明确的目标、范围、行为和验收条件写入计划，无正式编号时用本地编号。页面工作按下方“产物接入”判断是否需要原型，依据充分且已有实施授权时直接开发，不把原型形式选择作为所有页面任务的前置。 |
| 专业模式（用户指定） | 正式需求文档为前置；涉及页面开发时，还须有覆盖本次页面范围的 HTML 或结构图原型，纯后端/无页面工作不要求原型。已有合格成果直接复用，缺失或过期时列出缺口；已有生成/更新授权则调用对应技能补齐，否则询问用户提供还是协作生成。材料未齐可做调研与计划草案，不宣称最终可执行，不启动依赖缺失材料的页面或功能实施。 |

用户明确描述的目标和范围可作为计划依据，无须为了“已确认”再要求一次形式确认；仍有实质业务或方案歧义时按共用契约处理。只有已确定需要原型且制作方式未决，或关键布局/交互选择尚未解决时，暂停依赖它的部分；可继续不受影响的调研、草案和实施。专业模式若用户明确免除文档/原型前置，遵循其要求并标注具体豁免及替代依据，不能声称原前置已满足。

保存已有成果不因模式检查自动补建文档或原型。

## 执行流程

先区分新分析/生成、局部更新与仅保存已有成果；保存按文档编写规范处理，局部更新按范围读取 [任务与验证记录](references/output-template.md#任务与验证记录)，只执行受影响步骤。

1. **识别操作与输入**：确定模式，定位用户指定的自然语言需求、文档或技术工作目标，区分生成、保存和更新。对会改变交付对象、既有契约或范围的上游结论，先按共用契约核对授权依据，再拆分任务；需求编号和“已确认”标签不能替代来源核对。完整读取本次需求，提取来源、目标、范围、适用的角色/流程/数据/权限/接口、验收和未决项；按模式判断前置，不因缺文件否定明确的需求。同一成果按授权更新，不因已有文件另建平行计划。
2. **核实实现依据**：调研相关代码、页面、服务、配置、数据库/SQL、权限、测试及项目规范，记录关键路径、接口、类/方法、表字段和状态等可核实依据。缺少访问能力时标注限制，不猜现状。
3. **承接页面与原型**：涉及页面、布局、组件或交互时，读取 `DESIGN.md` 及适用的组件库、页面模板、样板和测试契约；没有相关规范时说明最低 UI 约束。按模式处理原型选择，已有引用必须实际读取，相对路径按引用所在文档目录解析；无需求文档时沿用本次功能目录，不虚构文档路径。按共用契约区分业务、呈现与实现的维护位置，页面条件及缺项补充边界见模板。
4. **判断阻塞**：按共用契约先核实事实，再处理实质业务或方案选择。阻塞未决可保存计划草案并标记依赖，不能宣称最终可执行或启动受影响任务；不受影响部分继续。非阻塞项写明影响、确认时点和到期依赖。
5. **编排方案与任务**：梳理总体业务流程与本次变化，确定实现思路和共用契约，以可交付业务能力编排任务、依赖及必要测试工作。逐项建立需求→任务→测试验证/业务验收检查点的映射，填写契约按模板维护。性能、安全、兼容、SQL、发布等按风险展开，发布操作串成可核验的执行顺序，不为套表引入新框架、队列、缓存或配置体系。
6. **交付计划或继续实施**：完整计划按模板生成，会话任务清单按入口规则组织；初始安排与执行证据分开。只请求计划到此交付；已有实施授权时按依赖顺序完成任务，复用共享入口，检查上下游与同根因问题，执行适用验证并修复失败，再按下述状态规则更新实际结果。必要依赖未解决只暂停受影响任务，不将草案或实现结束当作验证通过。

## 核心约束

### 产物接入

首次生成或整体重构完整计划前读取 [开发计划与实施固定模板](references/output-template.md)，其唯一维护产物结构、填写位置及专项方案内容要求。仅用会话清单实施时，仍执行测试规范和本技能的映射、状态及完成要求，不因未保存计划省略必要验证。

原型判断与交接按共用契约的 [原型必要性与交接](~/ai-agent-config/config/force/requirement/requirement-collaboration.md#原型必要性与交接) 执行，专业模式另满足模式表前置。制作、形式选择和验证交给原型技能，页面实现方案填入所属任务。

### 需求映射与状态规则

#### 编号与映射

- 沿用上游需求编号，不能重排或改义；无编号的输入可在计划内分配 `L1` 等本地编号并标明来源，避免伪装成正式 PRD 编号。后续正式编号出现时建立对应关系，不静默替换导致历史追溯丢失。
- 必须项、有编号的建议项和明确排除项均记录纳入判断；每个本次纳入项至少有一个任务，每个任务可追溯到需求、验收、现有约束或必要技术依赖。一个任务可关联多个强相关需求，映射逐项列出。
- 范围与需求阶段建议状态引用上游，不另设可选增强状态表；任务状态在任务条目维护，映射中的进度是汇总，更新任务时同步更新受影响的汇总。按模板填写，三个维度不能混为一个状态：

| 维度 | 值与含义 |
| --- | --- |
| 纳入判断 | `本次纳入`：已确认在本次做；`本次排除`：已确认不在本次做，注明依据/后续条件；`待确认`：范围尚未决定。不能擅自将必须项排除。 |
| 覆盖判断 | `一致`：计划完整承接；`部分覆盖`：有缺口及补齐任务；`未覆盖`：缺任务；`超范围`：计划内容无需求/约束/必要依赖依据；`待确认`：覆盖依据不明；`不适用`：已批准本次排除，不算漏做。覆盖判断描述计划承接，不证明实现完成。 |
| 执行进度 | 沿用下方任务状态定义，按汇总规则得到，不手工猜测。 |

需求总览每项需求独立成行，即使共用任务也不合并编号。共同的范围类别、建议状态、纳入及覆盖判断可在表前说明，例外逐项标明；三个维度语义独立，不能以一个“完成”覆盖。填写位置与详细程度按模板维护。

`部分覆盖`、`未覆盖`、`超范围`、`待确认` 必须关联补齐任务、范围决策、风险或阻塞；无法追溯的开发内容须解释必要性或移出计划。经批准排除的建议项用 `本次排除 / 不适用 / 跳过`，不能作为缺陷计入本次完成条件。

#### 任务状态与需求汇总

技术门禁与业务验证均由 AI 执行或核验有效的 AI 执行证据，并据此控制检查点、任务和需求进度。人工后续按同一用例复现，不另设人工验收状态，也不将人工执行、签收或确认作为开发验证及任务完成条件。AI 必要验证无法执行或证据不足时仍按实际缺口处理，不能转交人工后标为完成；后续发现真实失败时重新评估受影响结果。

- **任务状态**：初始 `待开始`；无未消除失败或阻塞时，开始实施或实现已结束但必要验证尚未执行为 `进行中`；必要检查或验收已有失败，尚未修复或修复后尚未复验通过为 `未通过`，保留失败证据及后续处理；无未消除失败但受未解决依赖阻止推进为 `阻塞`；产出及必要验证均满足完成标准才为 `已完成`；经范围决定取消或不执行为 `跳过`，注明依据。复验通过后按实际完成条件重新判定，不得以跳过必要验证完成任务。
- **本次纳入需求汇总**：必需任务或需求验收存在未消除的失败则 `未通过`，同时保留适用的阻塞说明；否则有阻断完成的未决依赖或必需任务阻塞则 `阻塞`；否则全部必需任务完成且需求验收证据满足才为 `已完成`；已启动或仍待集成验收为 `进行中`；均未启动为 `待开始`。没有必要任务或必需任务被跳过时记覆盖缺口并阻塞完成，不能按空集合或全跳过算完成。
- **范围未决**：汇总为 `阻塞` 并说明待决定的范围，不执行依赖它的任务。**本次排除**：汇总为 `跳过`，保留此前已发生的真实任务记录，不能倒改成“未做”。
- 单个任务完成不代表关联需求完成；可选且不属于完成条件的任务不阻断需求，需明确其依据。多需求共享任务时，需求各自检查验收，不用一个完成状态覆盖全部。
- 变更范围后重新核对编号、纳入判断、覆盖、任务依赖及汇总；只更新有证据的条目，不批量标完成。已有文档状态按这些语义核实，保存原文时不擅自改状态。

生成或更新状态展示时读取模板的 [状态展示](references/output-template.md#状态展示)，由该处唯一维护颜色映射。

## 产出边界与交付

交付会话任务、授权的 `plan.md` 或已完成的实现，遵守入口分支。保存和局部更新保留有效基线；实施交付说明实际结果、两类验证结论及未完成项，业务用例及直接引用应支持人工后续复现。

## 验证与完成标准

- 模式与前置状态准确：普通模式没有强制补 PRD，已说明页面实现依据及是否需要原型，只有进入原型分支才核对形式选择；专业模式的需求文档及适用原型真实、覆盖当前范围。缺口或豁免明确，不能把草案交付说成前置已满足。
- 检查需求→任务→技术门禁/业务验证双向可定位，无孤立需求、任务或必要检查点；按测试规范核对覆盖及可复现性，从单个任务及直接引用能判断依据、影响、操作和完成条件。
- 从接手开发者角度先读总览确认整体流程、本次变化与交付结果，再沿一条需求走到接口、处理、数据/状态、反馈与失败恢复；结合任务及直接引用能确定首个可执行步骤、关键契约和完成判据，无须补猜影响正确性的决定。新设计标待实施，不能只列技术栈或文件名。
- 本次纳入项无未解释缺口，每项任务有来源和产出；范围、覆盖与进度含义分开，必要验证缺失不算完成，排除建议不算漏做。
- 页面方案承接真实原型，或按本技能判定无需原型时的充分依据；专业模式的豁免仍须有用户依据。复用与配置有实际消费，适用的性能/安全/迁移/发布要求落到任务和验证，未额外引入无必要体系。
- 按模板的 [内容组织](references/output-template.md#固定结构的填写深度) 与 [发布、回退与交付要求](references/output-template.md#发布回退与交付要求) 检查任务、验证和发布依赖能顺序成立；实际读写主体、权限、版本、状态及观测时点一致，操作主说明与索引可直接查用。
- 沿代表性业务用例核对首次接触系统的人能否完成准备、操作和结果判定，无须阅读源码或猜业务规则；这属于用例质量核对，不要求另找人工执行。完成状态按上方 AI 验证规则判定。
- 文档与关联引用一致，实际结果有证据，未验证和阻塞如实披露；表格齐全不能证明计划可执行，不额外新建阶段性报告。

完整生成或整体重构后运行 `python3 <skills-root>/skill-authoring-standard/scripts/validate_document_template.py <plan.md> --template <本技能目录>/references/output-template.md`；实施与验收证据仍按模板单独核对。
