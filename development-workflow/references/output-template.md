# 开发计划与实施产物模板

本文件唯一维护开发计划的默认目录、片段落点与格式；模式、最低信息及状态语义由 [技能入口](../SKILL.md) 维护，通用结构与更新规则从 [共用契约](../../requirement-doc-authoring/references/workflow-contract.md) 接入。首次生成或获准重构时使用。

采用**默认骨架**，沿用下方主体目录。只有一个任务且没有跨任务依赖或独立交付安排时，可把总览并入开头；任务详情与具体完成条件仍须分别可定位。复杂任务展开所属片段，共用方案仅在跨任务生效时集中；SQL、发布与回退仅在实际涉及时启用。计划阶段与实施阶段沿用同一字段含义，不把待验证安排改写成已通过结果。

首次生成或获准补全边界时，在下方用途与归属位置填写实际来源和维护分工。

下列代码块中的片段链接与括号提示仅用于组装，生成时替换为实际内容，不写入交付文档。补充片段嵌入指定位置，不作为计划末尾的额外章节。
组装时同一对象的标题只保留一份，子项标题按所属位置嵌入。

## 状态展示

任务状态及需求汇总进度使用“彩色圆点＋状态文字”，映射如下；状态含义与汇总判断沿用 [任务状态与需求汇总](../SKILL.md#任务状态与需求汇总)。

| 状态展示 | 颜色 |
| --- | --- |
| 🔵 进行中 | 蓝色 |
| 🟢 已完成 | 绿色 |
| 🟡 待开始 | 黄色 |
| 🔴 未通过 | 红色 |

`阻塞`、`跳过` 保留文字并注明原因，不套用以上颜色。颜色只辅助识别，不省略状态文字；验收项的 `待验证`、实际结果及证据仍独立记录，不转换成任务状态。仅保存原文或与状态无关的局部更新不批量改色。

## 开发计划主体

```markdown

目标与范围：……（含不做范围）
来源与模式：……（文件/会话、原型或获准替代依据）
用途与归属：本文用于实施与交付，维护方案、任务、进度及实际验证结果；业务要求与验收契约沿用{有效需求文档或会话输入}，长期架构与设计规则沿用{已有权威入口或当前归属}，不在计划中另立定义。
当前结论：……（可执行范围、关键阻塞及证据时点）

## 1. 需求与交付总览
```

## 单个开发任务

```markdown
### T1：任务名称
对应需求/约束：……；输入与前置依赖：……（所需资料、接口/数据契约、前置任务及可用状态）
状态：🟡 待开始；验收：……（链接到具体检查点）

**目标与现状依据**
目标行为、已有能力及缺口；可核实的文件/API/数据/原型来源、已确认口径及限制。改变交付对象、既有契约或范围时，写明对应授权依据，不仅引用上游任务编号。

**实施方案**
复用、扩展或新增入口及理由；串联入口、处理、数据/状态、反馈与失败恢复。
说明修改入口、受影响消费方、保持不变的行为及必要回归；不要仅列修改文件。
就地展开适用的页面、权限、异常、性能、安全、兼容、SQL及风险；未决项说明影响和解决时点。
（涉及SQL时，在本节按[任务内 SQL 说明](#任务内-sql-说明)展开。）

**开发步骤与产出**
1. 具体操作、涉及文件/模块及产出。
2. 后续操作、依赖及产出；必要时拆子任务。

**完成条件与当前结果**
完成标准：具体产出及必需验收项/技术检查。
实际落地：待实施；后续填写真实产出、差异、证据入口和未完成缺口。
```

完成条件直接关联验收检查点。

## 验证项与执行结果

嵌入主体“3. 验收与交付 → 按业务流程验收”，按验证目标重复该单元。

```markdown
#### V1：业务流程或验证目标
共同关联需求与任务：……（仅适用于关联相同的检查点；不同关联在对应行注明）
前置：角色、入口、版本、环境、数据规模/负载及依赖；共用条件引用前文并补差异。

| 检查点 / 关联差异 | 操作或命令/用例范围 | 预期结果与通过条件 | 实际结果/证据/后续处理 |
| --- | --- | --- | --- |
| V1-01（无差异则沿用共同关联；有差异写需求及任务编号） | 一个可独立判定的操作或场景 | 可观察的反馈及数据/状态结果 | 待验证 |

执行后记录实际环境/版本、数据/负载、操作或命令、实际用例数（适用时）、结果和证据。
未执行或失败须说明原因、影响、关联任务和补测安排；部分失败分项记录。
```

自动检查与人工验收分别说明证明范围，不以编译、桩测试或合成页面通过替代目标环境闭环。性能验证按技能入口保留可比基线、资源占用、目标及未达标处理。实际结果引用已有记录时须能直接定位，不复制全量日志。

人工验收按真实操作顺序编排检查点，明确角色切换、数据准备、入口和交接；不按需求编号机械排序。已有需求验收条件时，预期列保留可直接判定的简短结果及具体条件引用，阈值和业务口径沿用该权威定义；跨任务补充交接与整体终态检查。标准用于判断，计划中的检查点承载执行顺序和实际结果，不能让验收者自行拼接多个需求才能完成一次流程。

## 任务内 SQL 说明

嵌入“2. 实施方案与任务 → 所属 Tn → 实施方案”。多个任务共用时由一个任务维护，其他任务及发布安排引用，不重复维护脚本契约。

```markdown
**SQL：用途**
- 文件路径、目标及前置条件：
- 结构/数据变更、影响范围与历史兼容：
- 执行时机、顺序、重跑条件及核验：
- 回滚方式或不可回滚原因：
```

## 发布与回退

展开主体“3. 验收与交付 → 发布与回退”；集中维护跨任务交付安排，SQL细节引用所属任务。

```markdown
### 发布与回退
- 目标环境、版本/产物及前置检查：
- 产物接收方与交付方式：复用既有发布渠道/入口；未知时写明需确认内容及阻塞的交付步骤。
- 构建与发布步骤：执行入口、产物生成/取得方式、部署操作及执行顺序；已有流水线引用其实际入口与前置条件。
- 初始化或升级顺序：引用任务中的SQL、后端、前端及菜单/权限配套。
- 配置/环境变量、生效方式与启用条件：
- 健康检查、成功判据、监控及回退触发条件：
- 回滚前提、步骤、数据保留及回滚后核验：
- 当前结果、未完成条件与后续处理：
```
