## 状态展示

任务状态及需求汇总进度使用“彩色圆点＋状态文字”，映射如下；状态含义与汇总判断沿用 [任务状态与需求汇总](../SKILL.md#任务状态与需求汇总)。

| 状态展示 | 颜色 |
| --- | --- |
| 🔵 进行中 | 蓝色 |
| 🟢 已完成 | 绿色 |
| 🟡 待开始 | 黄色 |
| 🔴 未通过 | 红色 |

`阻塞`、`跳过` 保留文字并注明原因，不套用以上颜色。颜色只辅助识别，不省略状态文字；验收项的 `待验证`、实际结果及证据仍独立记录，不转换成任务状态。仅保存原文或与状态无关的局部更新不批量改色。

## 填写与内容验收

### 固定结构的填写深度

完整结构及填写位置由上方固定模板维护；任务及汇总状态语义沿用技能入口。

实施范围由需求总览维护，不另设范围或增强状态表。以具体业务能力、SQL变更、配置项或恢复操作为对象，在所属任务或最便于独立查用的既有说明中就近组织依据、适用范围、限制、操作、核验与结果，完整主说明只维护一处；其他位置保留当前阅读所需的摘要、索引或直接引用并补实际差异，不按信息类别强制拆散同一对象。跨任务共用规则集中维护，消费任务引用并补差异；脚本和代码仍保留规范要求的必要说明。性能、安全和兼容性始终判断适用性，低风险在对应固定字段说明依据。下表说明各处用途及填写深度：

| 主题 | 最低内容 |
| --- | --- |
| 来源、目标与范围 | 输入文件/会话依据、目标、不做范围、项目事实及限制、输出位置；建议项沿用需求阶段状态，不能自动纳入。 |
| 技术方案 | 第二章整体思路保留全局概述、关键单元职责与取舍，区分逻辑模块/运行服务/一次性任务；跨任务共用的数据流、接口、状态、权限及兼容契约在S项完整维护，任务引用并补自身差异。单任务方案在第三章所属任务展开入口、处理、数据/状态、反馈及业务失败恢复。 |
| 需求映射 | 每项来源、范围类别、需求阶段处理状态（如有）、纳入判断、计划开发内容、任务、覆盖判断、进度及缺口。详见技能入口的映射规则。 |
| 任务与依赖 | 第三章使用固定任务条目，具体深度按[任务与验证记录](#任务与验证记录)；总览汇总进度，第五章记录交接情况。 |
| 测试与验证 | 第四章V项分列技术门禁与业务验证；按[引用与展开规则](#验证计划与实际记录模板)组织步骤及结果，通用充分性要求沿用技能入口已引用的测试规范。 |
| SQL变更 | 所属任务说明变更设计、迁移原因、适用对象与脚本入口、执行前提/方式、兼容与重跑限制、核验和恢复；已有完整脚本或迁移说明时引用并补差异。脚本按编码规范自带必要执行说明；发布章聚合操作索引、目标环境及跨任务执行顺序。 |
| 配置项 | “配置变更总览”供读者判断涉及哪些项目、改哪些项及人工待办；完整操作在“发布操作明细”或已有主说明中维护。定义与消费、适用值/作用域、配置操作、生效和核验均须可定位；共享配置模型与环境实例确有独立用途时可分别说明并直接关联。 |
| 发布顺序与恢复 | 第五章串联本次发布的全局顺序，引用SQL、配置及恢复对象的完整说明；“失败恢复与重新放行”承接发布级协调与尚无完整说明的恢复操作。局部恢复的触发、前提、步骤、数据限制和核验可在任务、脚本或手册中完整承载。 |
| 风险、假设与未决 | 依据、影响、处理动作和确认时点；阻塞项明确关联任务，最终可执行计划不得掩盖未决阻塞。 |

总体业务说明让首次接手者在阅读任务前理解为什么做、谁从哪里开始、经过哪些关键处理或交接、以什么结果结束，以及本次改变和保持什么。简单修复用短段落说明触发与行为差异，纯技术工作说明触发方与可观察结果；复杂链路可配流程图，不强制画图。保留必要术语与业务口径，详细规则引用上游，任务编号与状态由下方总览表维护，不复制 PRD 或技术方案。

仅单任务适用的内容留在该任务，不把任务细节或原有各章整体搬入共用方案。没有跨任务方案时，整体思路仍需填写，共用方案重复单元用 `条目情况：不适用：原因` 说明，不虚构共享对象。

实施顺序说明任务之间的先后、并行及交接条件；任务内操作和发布操作分别在所属步骤展开，用引用连接，不在三处重复维护完整操作。

填写深度随实际决策和操作复杂度变化。简单改动可用一个任务承接实现与验证；各项只补充对应位置需要的信息，已有规则、命令和判据用具体引用连接，不在目标、方案、步骤、完成条件和发布安排反复重述整套内容。共同的不适用原因说明一次，相关字段简短引用；未启动任务的实施结果可直接写待实施，不重复罗列尚未开发、测试和发布。不得为补齐模板增加独立交付任务、文档或验证层级。

### 页面、复用与配置方案

页面方案按有效项目模板覆盖适用内容，嵌入所属任务的实施方案；按共用契约引用需求行为和已有页面方案/原型，重点展开实现关系与差异。已有区域、操作路径和状态呈现不再完整重述，共用设计保留一处，不再填写通用设计模板或复制全局页面映射表。

复用治理的检索与选型依据写入所属任务的“目标与现状依据／实施方案”，消费者与迁移写入“影响与保持项／开发步骤与产出”，完成条件关联验证检查点，实施结果引用其验证结果。保留各候选的对应关系，不粘贴独立反馈片段的标题和字段，不新增一套复用明细。

- 逐项承接自然语言或文档中的页面功能点，以及已有原型的相关区域，建立“页面功能点/正式或本地编号 → 实现与组件/模块 → 数据/API、状态/事件、校验、权限、联动与异常 → 任务/验证”的映射。写入所属任务并关联需求总览，但不能只写“按需求实现”。未纳入项按范围规则记录，不把排除项误标为超范围开发。
- 新增或复杂页面承接页面类型、主操作/内容/辅助区、弹层/抽屉、固定与滚动归属、增长区域、窄屏和低高度退化；已有定义引用到具体区域并说明实现，不另维护布局副本。更新页面说明变更区、保留区及兼容影响。布局依据关联实际原型，或按技能入口判定无需原型时的现有页面/规范/文字方案，任务承接主要入口、数据区和加载/空/错误/权限等状态；没有上游页面方案时在此展开。
- 原型选择与专业模式前置沿用 [技能入口](../SKILL.md#产物接入)，具体格式制作与验证由原型技能维护。
- 页面方案未覆盖的关键状态和交互按性质补充：既有行为的实现细节在任务中补清，呈现缺项补入当前有效页面方案并引用，业务行为变化按共用契约更新需求来源及受影响内容；不能只在计划中形成新业务口径。
- 运行时组件先判断现有能力能否覆盖，写明共享入口、真实消费页面、状态/事件契约及验证；不足时先扩展既有能力，确需新增才拆组件产出、至少一个真实样板接入、必要清单/规范维护和验证任务，禁止套外壳后重复手写同类行为。
- 涉及布局、组件配置或页面注册时，确认项目实际机制与事实源：自动发现/继承只验证真实消费，不新增逐页登记；显式登记按本次契约补配置 schema、必要登记、存储、读取与生效；没有平台时不为表格新增体系。不适用环节说明原因即可。
- 配置、偏好、模板和预设覆盖定义/渲染、模型与默认值、权限/作用域、校验、保存、读取、实际消费、生效、重置、回退及旧值兼容。跨场景基础能力先核心模型与约束，再真实样板，最后渐进接入，明确迁移与不做范围。
- 页面方案内融合适用设计和组件/布局维护要求，不能用一张登记表代替实现；页面验证按测试规范的前端专项入口选择场景。

复杂页面在任务的实施方案字段内分条展开；复用/扩展/新增判断、接入机制、必要登记及实际消费必须可辨识，不能借表格增加配置体系。

### 性能、安全及其他条件方案

性能、安全和兼容性均需作适用性判断；低风险在性能、安全与兼容字段说明依据，有实质目标/风险则在该字段逐项展开，并引用需求编号或现有约束。不应把“不适用”写成未核实的“无影响”，也不虚构默认指标。

| 条件 | 必须承接的方案信息 |
| --- | --- |
| 性能与容量 | 需求目标、现状基线/瓶颈、数据量/频率/并发/时限与统计口径；按需选择查询/索引、分页/分批/流式、缓存一致性、异步、事务范围、远程去重与超时、资源上限/释放、前端加载/渲染/请求、降级与容量方案，写明取舍、位置、任务和验证。 |
| 安全、权限与数据保护 | 保护对象、信任边界、入口/数据流及风险；按需说明认证、功能/数据权限、输入/输出、文件/富文本/外部地址、敏感信息传输/存储/展示/日志、凭据、会话/令牌、重放/幂等/限流、审计和第三方依赖；每项写明校验位置、失败默认行为、任务、正反向测试及剩余风险。 |
| 后端与第三方 | 服务与接口契约、事务、日志、异常、幂等、一致性、性能影响；第三方的超时、重试、降级、审计和联调。仅展开实际相关项。 |
| 数据库与 SQL | 设计与执行信息按任务的SQL字段和上方填写深度维护；脚本按 [编码规范“写SQL时”](~/ai-agent-config/config/force/coding-standards.md#写sql时) 自带执行说明。迁移、补数等另承接下方专项差异。 |
| 发布部署 | 构建产物、目标环境、配置生效、初始化与升级的区别、前检/发布步骤/健康判据、监控与回退条件；通用流程与环境实例参数分开，未知参数标待确认，不编造可直接执行命令。 |

性能与安全实际改动必须落到任务、相应验证、必要监控/告警、上线检查、发布/回滚影响及剩余风险。缺少基线、指标或安全边界时，说明具体阻塞的方案决策、达标结论或环境操作，不能只写原则、工具名或“沿用现有机制”。实验授权、隔离边界和停止条件已明确时，可继续有界基线采集、正确性验证及参数试验；常规实验候选值标明依据与待测状态，不冒充业务指标或生产值，也不一律要求另行批准。开发环境不能完成的容量验证要写预发或上线后步骤、责任边界和回退条件；未执行验证不能算已通过。

有实质性能或安全方案时在所属任务中展开上述信息，在固定字段内分条说明；仅跨任务共同生效的约束进入共用方案。

### 专项工作的方案与验证

按共用契约识别工作类型，将适用信息补入技术方案、具体任务、验证及必要发布/回滚条目；复用上游契约，不复制一份专项需求表。下表是条件最低内容，不要求每次展开全部类型，也不自动执行所列操作。

| 工作类型 | 方案、任务及验证必须承接的内容 |
| --- | --- |
| 缺陷修复 | 复现条件、预期/实际与证据；区分已证实根因和待验证假设，安排定位任务及影响链路检查。回归应能检出原缺陷并验证修复及相邻边界；无法重现旧故障时说明替代证据、验证限制和剩余风险，证据不足时不得声称根因或修复已证实。 |
| 重构或升级 | 保持项与允许变化、共享入口及受影响调用方、依赖/接口/配置兼容；涉及替换时，将新旧切换、调用方及测试/门禁迁移、旧入口与失效文档清理纳入同一交付闭环；需保留旧实现时写明仍在使用的依据。以契约回归或新旧对照验证行为，说明允许差异；仅编译通过不能证明行为等价。 |
| 数据迁移、补数或修复 | 在SQL/数据变更主说明补清精确选择条件、源/目标及转换口径、写入顺序与并发约束、试跑与备份、长批次断点与部分失败处理；前后核验数量、关键值与业务不变量，解释差异和残差。无法回滚时明确前向恢复及停止边界；发布章安排全局时机，V项引用核验并记录结果。 |
| 异步或第三方链路 | 在后端与第三方契约中补清受理到终态的回调、状态迁移、持久化/查询及完成信号；按实际机制说明超时、重试上限与停止条件、去重、乱序、部分成功的补偿或人工接管，关联失败验证与必要监控，不凭空新增队列或补偿系统。 |
| 从零建设或技术验证 | 涉及可运行产物时明确依赖与版本/环境约束、初始化顺序、启动入口和首条可运行链路；未知选择安排有边界的验证任务。验证任务写明假设、实验输入/方法、成功/失败/停止判据及证据，结果回填结论与生产落地缺口；假设被否定也可完成验证任务，不能据此将生产实现标完成。 |

专项信息可追加到现有模板字段或就地引用；每项适用要求须关联任务与具体通过条件，实际证据仍按“任务与验证记录”填写。用户只要计划时保留待实施/待验证，不为补齐证据擅自修复、迁移或部署。

### 任务与验证记录

任务按依赖顺序排列，以可独立判断结果的业务能力为粒度；同一能力的前后端、数据与页面操作在任务内按步骤展开，必要时拆可追踪子任务。多个能力共同依赖且有独立产出的基础工作可设共享任务；不把无依赖关系的大块工作塞进同一任务。接口契约确定前不安排依赖它的联调，实现之后安排对应回归；前置测试设计可先进行。区分契约确定、实现可用与验证完成，任务依赖与验收前置不能形成完成条件循环。

更新时就地维护有效方案、实施结果与剩余事项，同步受影响的当前结论及需求汇总，不按日期或命令顺序追加平行方案。任务状态只记录进度及失败/阻塞定位；完成条件引用必需检查点；实施结果说明实际交付的文件/模块、关键行为、差异、降级及缺口，验证结论引用V项。V项关联AI实际验证记录，已有详细证据直接引用，没有承载处时就近记录；第五章交付结果维护实际交接情况，不重复测试输出或新建过程文档。生成计划前已完成的工作按有效证据填写，不套用初始状态。

现状注明可核实来源，未决说明影响、处理动作与解决时点。任务总览表不能替代详细任务。

实施方案展开会改变正确性或跨任务协作的关键契约：接口的输入输出、必填/默认值与错误语义；状态的转换条件、重复或并发处理；数据的字段含义、约束、事务与历史兼容；权限的实际读写主体、允许操作、校验位置及拒绝结果。仅展开实际相关内容，已有可靠定义引用到具体位置并补本次差异，共用契约只维护一次；SQL与性能、安全等细节仍归对应字段。区分已确定的业务规则与技术选择；引入更强的一致性、全局互斥或可用性限制时，须有实际必要性和取舍依据，证据不足先安排有界验证，不将增强目标写成上游要求。常规内部编码细节留给实施，不预写全部代码或逐方法设计。

开发步骤按依赖顺序指出在什么真实入口或层次做什么修改、形成什么产出、如何判断结果或处理失败，以及何时具备供后续任务使用的条件；新增位置明确为拟新增。执行者结合任务及其直接引用应能开始工作，无须补猜关键业务或技术决定；缺少这类决定时列明缺项和阻塞范围，不用“按规范处理”掩盖。现有资料可核实的细节先调研，低风险常规选择自主处理，不因此增加确认环节。

影响范围须包括修改入口、受影响消费方、保持不变的行为和必要回归，不能用修改文件清单代替。性能、安全、兼容及SQL的独立约束保留在对应字段，开发步骤就近说明其适用影响，不重复完整契约。

#### 验证计划与实际记录模板

第四章按V组组织验证目标或业务流程，组内分别维护技术门禁和业务验证点。两类用例的覆盖、操作深度和证据按测试规范核对；检查点及任务完成状态沿用技能入口的 [任务状态与需求汇总](../SKILL.md#任务状态与需求汇总)。先核对既有说明对本次对象、版本及场景的覆盖，再选择：

- **完整覆盖**：直接引用可定位的说明，补本次执行条件、结论与证据。
- **部分覆盖**：引用已有部分，仅补缺失步骤、判据或实际差异。
- **没有可用说明**：在V项编写检查安排。

每个可独立判定的检查点有稳定编号。组头声明共同需求/任务，检查点注明关联差异；技术检查关联所属任务及适用约束，不虚构业务需求编号。跨任务流程只写一次，每个检查点能定位受影响任务；共用环境与数据放第四章开头，组及检查点补差异，不能只留下“补测试”的汇总任务。某类验证不适用时保留分区，在该处填写依据。

验证前置写清所需实现和环境何时可用：本地/隔离环境检查、部署前检查和目标版本部署后的验收分别关联相应步骤，不机械分组。部署后的验收关联V项，已有完整操作核验直接引用，发布步骤说明执行时机及相应失败处理。检查依赖一次性动作或暂态时，写明如何建立该条件及何时采集证据，不能在动作结束或所需版本退出后才安排观察。依赖部署的验收不能反作首次部署的前置；此时先以已完成的必要前检进入受控部署，再执行目标环境验收，未通过前不标最终完成。既有流水线没有中间暂停能力时按真实阶段安排检查和失败恢复，不为计划新增未经依据的人工门禁。

需补写的复杂检查在对应分区表前正文槽位按标识展开准备、编号步骤、判据及适用分支，技术命令使用代码块；表内保留摘要、详情定位及本次AI结果。简单检查直接写表。性能比较写入本组“性能与容量对比”；失败与未执行项关联受影响任务和后续动作，不将技术门禁的通过结论填入业务验证结果。

页面检查关联有效原型或页面方案，配置与组件检查关联本次方案中的实际消费及生效契约，基础能力关联真实样板；需求与页面功能点已有可操作验收时直接引用，不维护平行清单。

### 发布、回退与交付要求

本章按固定模板组织，按实际涉及的部署、数据与配置变化填写。在“发布范围与执行顺序”判断首次安装或存量升级的适用路径；两种路径都适用时说明初始化、任务SQL、后端、前端及菜单权限配套的差异，差异操作写入对应发布步骤，共同步骤只写一次；仅适用一种时说明依据。未知环境参数和命令标待确认并指出补齐来源、时点及阻塞步骤，不能拿占位内容作为可执行指令；沿用来源明确的交付或核实时点，不能为减少阻塞将“交付前核实”改为“执行前再补”。条件未满足时可交付标明缺口的草案，相应最终交付项仍未完成。

仅交付源码、文档或实验结论且不涉及部署、数据或运行配置操作时，在“发布范围与执行顺序”统一说明依据；其余节只写实际需要的构建/打包、配置、成果核验与交付事项，无操作的节简短引用该范围，不展开重复的安装、服务健康或线上回退流程，不索要无关生产参数。“交付结果与后续”集中维护交付对象、接收方、渠道、实际结果和剩余条件，默认沿用用户指定路径、当前工作区或会话；只有实际需要外部交接且渠道缺失时才列为未决，不为普通本地交付另索接收人或审批。

发布章是交接操作入口：读者从本章及其直接链接，应能确定本次要发布哪些项目、改哪些配置、执行哪些SQL及先后关系，无须跨任务拼凑。按实际涉及对象在既有正文槽位用表格或列表集中对应，不为补齐模板机械新增交付文档或发布无关项目；用户已授权或项目要求的独立交付材料按需维护并直接引用。

第五章固定为“发布范围与执行顺序、配置变更总览、发布操作明细、失败恢复与重新放行、交付结果与后续”五节，不再增加“构建与发布步骤”包裹层。第一节先说明范围、前提和缺口，再用编号建立发布路径；总览用于查配置差异，操作明细沿同一执行编号顺排；构建、SQL及配置的完整操作就近放入对应步骤，不再拆成平行章节让读者跨节拼接。配置准备在依赖它的构建或服务启动之前，保存配置与实例实际加载分别核验；启用、解除停写及失败恢复条件在合并后仍完整保留，不能用健康检查代替必要业务核验。

“发布操作明细”按骨架使用可重复的四级操作子章节，标题由全局执行编号和操作名称组成，编号唯一、稳定，顺序对应第一节，可从目录及直接链接定位。步骤名称、数量和编号体系按本次实际确定，不固定为R1—R6；简单发布可只有一个操作章节。没有实际操作时不造空步骤，在本节写明 `条目情况：不适用：原因`。共用前提放父节，各步骤承接自身前提、操作、核验和失败去向，不重复维护配置值或已有完整主说明。多批次发布按实际对象明确步骤、配置及核验的适用范围，保留跨批依赖，不把某一配套组的专属条件套用到无依赖批次。

配置变更总览按实际技术用途分表，例如构建环境、项目运行、菜单权限、业务配置与初始化；不固定类别名称和数量，单一类别使用一张表。每类以骨架中的四级标题命名，沿用相同表头；配置项编号跨类别保持唯一和稳定，分类不改变全局执行顺序或配置的实际处理时机。没有配置变更或核对时，不输出虚构类别，在“配置变更总览”写明 `条目情况：不适用：原因`。

分类表逐项覆盖本次涉及的配置，已有详细说明也须保留总览行。表中写清项目/服务与环境、准确位置和键/字段、前后值或取值来源、处理类型、人工待办及执行时机；同一项在不同项目、作用域或处理动作不同时分行。处理类型覆盖新增、修改、删除/移除、停用等实际动作，可组合条件性、自动执行、保持或待开发说明，不作为互斥枚举。人工待办给出核对、填写、授权、撤销等具体动作，无须操作明确写明；条件性修改写触发条件，删除/停用写明变更后的状态，未知值标出缺项和取值来源，密钥不写实值。开发未完成列为待开发，不能包装为让用户填配置即可启用。

总览首列显式关联定义、接入或消费该配置的T任务编号及可点击链接；单任务配置关联对应任务，跨任务共享配置列出相关任务并按需注明各自作用，同一配置不因关联多个任务重复登记。任务在实施方案中沿用同一配置编号，完整说明仍按原有主说明维护。仅属环境或发布准备且无直接开发任务时，写明“公共发布前置”及依据，不为填表虚构任务；关联尚未核实时说明来源缺口及影响，不猜编号或用公共前置掩盖缺口。关联任务说明开发追溯，末列的全局执行编号说明发布时机，两者不能互相替代。
