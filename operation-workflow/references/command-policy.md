# 操作场景、默认权限与通配规范

本文定义命令选择、场景模式、例外规则与匹配语义。实际默认配置只在[默认JSON](../assets/command-policy.json)，项目生效配置在`OPS_ROOT/command-policy.json`；执行和留痕分别见[主流程](../SKILL.md)、[记录契约](records.md)。

## 先选场景和默认行为

先定位服务器、身份、管理入口及操作目的，再选原生、直接命令。查看状态不用重启试探，核对配置不用重新部署试探；普通过滤、排序、格式和有限采样由执行者自行选择，不为参数拼写反复申请权限。

每个场景只选一种模式，根据该场景实际常用操作中需授权与免授权的分布，以及例外维护成本确定；不统一强制默认询问，也不按任务复杂度分流。

| 模式 | 适用情况 | 唯一例外表 | 未命中例外时 |
| --- | --- | --- | --- |
| 默认放行：`default: allow` | 常用操作以免授权为主，需授权操作容易集中列出 | 只配置`ask`，不配置`allow`，即使空数组也不允许 | 直接allow |
| 默认询问：`default: ask` | 常用操作多需授权，只有部分操作可直接执行 | 只配置`allow`，不配置`ask`，即使空数组也不允许 | 返回ask；人工确认统一按主流程处理 |

禁止行为统一维护在顶层`deny`，对所有场景生效。禁止项是共同红线，不是第三张与两类例外平行维护的常规权限表；不能为同一场景同时列放行表、询问表，再推测谁更具体。

默认配置中，Docker采用默认放行，仅列变更、执行、传输发布、切换管理端点及受限内容等询问例外；不枚举Docker查询白名单。其他命令采用默认询问，仅列免询问查询，不再重复列一大批本来就会询问的命令。未覆盖场景返回ask；已命中默认放行场景的未知子命令也继承allow，不能再用“未识别”暗中改回白名单模式。更新工具或改变使用范围时复核询问例外。

## 操作类别与规则取舍

- **通常免询问**：身份/版本、列表/状态/元信息、资源快照及普通诊断查询。在默认放行场景不写规则；在默认询问场景只把实际要放行的查询写入allow。
- **通常需询问**：启停/部署/更新/删除，文件/权限/账号/网络变更，容器内exec及脚本执行，受限内容或业务数据访问，导入导出/对外发布，以及超出任务边界的持续或高开销采集。在默认放行场景写ask；在默认询问场景不再列同义ask规则。磁盘格式化、覆盖写有合法用途，属于高风险询问，不按工具名一刀切禁止。
- **建议禁止**：泄露秘密、绕过身份/主机核验、越过明确禁止范围、删除系统根目录等不允许的行为或对象。只写到共同deny，普通任务批准不能覆盖；改变禁止边界先明确修改策略。

allow只决定动作是否免额外询问，不代表任意目标、秘密输出或无界采集。执行前选定对象、字段、行数和时间窗，统计默认快照、事件查询默认有截止时间；普通诊断自行裁剪/脱敏，不因潜在敏感字段就整体增加审批。不向工具回执、对话或Git输出私钥、密码、Token、进程环境或含秘密的整份配置。数值有效性、路径归属、秘密和业务范围由执行者核对，通配器不判断这些语义。

复合部署/构建入口可以整体作为询问例外，不再从该例外中逐条加白名单豁免。确需单独管理其中的查询时，为该入口建立独立场景并重新选模式，而非在原场景恢复两张相反的常规权限表。

## 配置契约

顶层仅有`version`、`targets`、`approval_ref`、`deny`和`scenarios`。版本为正整数；targets是精确的`{server_id,user}`对；approval_ref指向真实采用/批准来源，未采用时为null，不能伪造批准。场景只含`name`、`prefix`、`default`以及与默认行为相反的一张例外表。

下列是模式写法示意，完整配置以默认JSON为准：

```json
{"name":"docker","prefix":"docker --host unix:///var/run/docker.sock","default":"allow","ask":["{run,exec,rm} **","service {create,update,rm} **"]}
```

```json
{"name":"general","prefix":"","default":"ask","allow":["id **","df **"]}
```

prefix是实际命令的字面量参数前缀，不支持通配；固定程序、已核实管理入口或明确子入口。空prefix表示兜底场景。Docker命令和prefix先按下节做同样的参数规范化，再选参数前缀最长的唯一场景；不合并其他场景的例外，不依赖数组顺序。例外只匹配去掉prefix后的参数，因此Docker规则直接写`service update **`，不反复抄完整socket前缀。

## 通配写法

| 写法 | 含义与用途 |
| --- | --- |
| `*`、`?`、`[abc]` | 在一个参数内匹配，不会吞掉额外参数；例如`systemctl restart *.service`不含其他选项 |
| 独立`**` | 匹配零个或多个完整参数；例如默认放行Docker的询问例外`service update **`覆盖该变更的参数组合 |
| 整个参数的`{a,b}` | 新场景格式的单参数备选，可包含参数内glob；例如`service {create,update,rm} **`合并同类风险动词，`** {--context,--context=*} **`覆盖分开与等号形式 |
| `prefix` | 精确字面量前缀用于选场景；场景边界固定后，例外内不再重复它 |

命令及模式按shell引号分词，引号本身不参与匹配。备选组不允许嵌套、空项或将`**`放入组内；只占一个参数，不是shell执行或多段命令。Go模板的双花括号保持字面量含义。实际执行中的未引用通配、花括号展开、变量、命令替换、控制符、重定向及组合命令不会直接allow。

这不是文件系统路径glob：`*`能匹配同一参数里的`/`，不能阻止`..`、软链接或跨目录逃逸。路径限制须核对实际规范路径与任务边界，不能把字符串命中当作隔离。实际执行使用具体对象，不原样执行规则里的`*.service`。

例外动词放在实际子命令位置，避免`** rm **`把查询对象名`rm`误认成删除。参数例外需覆盖短选项、长选项及`--flag=value`；备选组用于合并相同位置的变体，不用大量重复整条命令。默认询问场景的allow须能独立表达安全范围，不能再配ask补洞；表达不了就收窄该allow，或把整个子入口另设场景后选择默认放行模式。

Docker只在根命令和已识别管理命令的子命令之前解析全局参数：按参数元数识别长选项、等号形式、短选项及短选项连写；匹配时移除debug/log-level/help/version等显示参数，统一同义全局参数写法，保留host/context/TLS等会改变目标或安全边界的参数供例外匹配。操作数、inspect对象名和exec负载保持原样，不用`**`猜测动词位置。未知或不完整的前置全局参数返回`unsupported-docker-options`，不能落入默认allow。全局参数语法统一在原判定器处理，权限仍由项目策略决定。

Docker共同deny先保留原始参数匹配，再将规则和命令交给同一个解析函数转为规范形式配对匹配；即使命令已经是长选项形式，也必须复核短选项或等号形式写成的规则。布尔开关的隐含true及1/0、t/f等写法统一，true与false保持区分。回执pattern始终保留原规则原文。规则中的显示开关同样被忽略，不用它们收窄底层禁止操作；参数值的glob和单参数备选继续有效，操作数不作全局参数转换。Docker规则须有可确定的程序名及全局参数/命令前缀，仍支持`docker **`等整类禁止。歧义前缀、不支持的全局语法，或备选展开超过256个变体时返回`invalid-policy`，不得忽略该deny后继续默认放行。非Docker规则及旧格式保持原匹配语义。

同一变更入口的官方别名必须同判：例如`rm/remove`、`stack deploy/up`、`stack rm/down`。将别名并入原风险动词组，不为每个别名复制一份完整规则；测试同时覆盖真实变更、全局参数变体和同名查询对象。

## 判定顺序与执行边界

1. 先校验策略。读取失败或格式损坏返回`ask / invalid-policy`，立即停止依赖操作；恢复有效版本、重新核对deny并再次判定后才能继续，不能凭已有批准或单次对话授权绕过损坏策略。目标不符另行核实，不当作已覆盖目标。
2. 匹配共同deny，命中立即deny。
3. 核对shell语法、展开及包装；不能静态直接分类的组合、解释器和脚本返回ask。
4. Docker用同一解析函数规范化命令、前缀和共同deny规则；无论命令是否发生转换，都先复核规范形式的规则与命令，再选唯一场景和匹配例外。命中用例外决定，未命中用场景默认行为。无场景返回ask；没有真实采用来源时不能allow。

分类结果如何转换为人工决定，统一读取[主流程的审批判定](../SKILL.md#审批判定)；本节不另定义任务审批触发或批准范围。

SSH按连接白名单核对后，只对远端内层命令分类；不把传输包装的ask当成新的连接审批。sudo、脚本、解释器及组合命令展开核对完整动作，任一deny即停止；包装ask不能自行当作allow；需要确认时执行主流程的当次命令确认，或选择能够准确判定的等效直接命令。API、SQL及文件工具按同样对象和副作用判断。

连接白名单仍由项目access-policy与servers.yaml维护，核对地址/端口、账号/渠道、凭据引用及可信主机指纹。命中后连接和重连不另批；默认不转发、不提权，身份或指纹不符先停下核实。连接放行不扩大远端操作范围。

## 执行方式

优先复用已核实的维护入口和直接命令；只为稳定复用或明确误操作防护编写脚本，不为留痕、包装SSH或统一输出搭建执行框架。方案列明目标、对象、步骤、影响及恢复条件，不预写具体命令。执行时从已核实入口生成当次命令并判定权限；使用脚本先审阅真实内容，不能以“执行脚本”隐藏内层动作。执行后记录实际命令或所用脚本的持久入口与版本，按记录契约只保存一处。

实施、验证和回退分别核对，异常先查已完成动作及实际状态，不盲目整段重跑。自动重试或条件回退逻辑须先在可控环境验证对应分支；条件未知时停止依赖步骤，不在目标服务上首次试验自动恢复逻辑。

## 宿主接入

[hook_command.py](../scripts/hook_command.py)适配调用前事件：宿主PreToolUse → 精确SSH目标 → 原check_command.py分类 → 当次命令确认或继续/停止。它不执行候选命令，不维护第二套权限表，不创建方案快照、批准编号、批准数据库或独立审批界面。任务范围批准与命令确认的分工统一消费[主流程的审批判定](../SKILL.md#审批判定)。

AI在执行当次生成可直接执行的命令或参数，再进行规则判定。方案只记录目标、范围及步骤；执行明细在操作后回写真实命令和结果，不预先展开、冻结整套命令。allow继续，deny/异常停止，ask在执行过程中确认本次命令。平台自身要求的执行权限仍使用其原生授权机制，不以任务确认代替。

| 宿主 | 当前Hook响应能力 |
| --- | --- |
| Claude Code | allow不追加许可；ask返回PreToolUse permissionDecision=ask，由宿主执行流程取得当次答复；deny/异常阻止 |
| Codex | allow继续；deny/异常退出2阻止。ask先暂停并返回当次命令的结构化问题，AI使用request_user_input_async展示这一个问题、先说明用途和影响并等待答复；用户选择“执行本次命令”后，AI重试原命令，Hook从宿主只读历史核对真实问题和答复后允许一次。取消/拒绝不重试；宿主自身执行权限照常保留 |
| Kimi Code | 当前Bash及旧Shell输入兼容；退出0继续、退出2阻止，其他错误码可能被宿主放行。此适配器尚未接通原生ask响应，ask阻止并明确报告能力缺口 |

原生ask和AI问询是两种确认衔接方式，不能因Hook不支持直接ask就把方案改成命令清单。Codex问询桥接只解决项目命令策略的人工决定；例如平台执行权限为never时，仍不能申请沙箱提权，但可以在已有平台权限内确认任务操作。不能改变宿主权限来制造弹窗。Kimi尚缺可核验答复的适配，不能用文件标签或工具参数伪造支持。

Codex重试核对当前原生会话、项目、答复所属turn、真实用户消息及其对应的原生问询；问题绑定本次完整命令、目标身份和策略版本。问询工具不可用或用途受限时，说明原因，在最终消息原样展示问题标题，空一行附`请回复“执行本次命令”或“取消”。`，等待真实用户答复；Hook仍核对宿主保存的问答。不接受旧方案批准、AI写入的approved字段、其他会话、改动后的命令、未回答或被拒绝的问题。

答复核验只读宿主thread/read与thread/items/list，不恢复或启动模型任务，不同步回执到文档。`.local/operation-hook-used/`每个会话追加保存已核销答复ID，持锁检查已有记录后追加并落盘；后续答复不会覆盖旧ID，旧式单ID文件按一条记录保留。日志不能创建授权，单文件上限2,000,000字节，达到上限或无法读写时停止，不自动截断、轮转或删除旧记录。答复查询失败保持暂停。执行结果未知不自动重试，重新执行须重新确认。

配置预览在启用前或下述技能维护入口运行，只输出到stdout，不覆盖设置、改变沙箱或自行信任Hook：

```bash
python3 <技能目录>/scripts/hook_command.py --host codex --project-root <项目绝对路径> --print-config
```

host可取codex、claude或kimi。Codex合并到项目`.codex/hooks.json`，Claude合并到项目`.claude/settings.json`，Kimi合并到用户`~/.kimi-code/config.toml`；只注册调用前判定，不注册方案批准监听。Codex问询桥接依赖已安装CLI和可读的原生会话历史；缺少有效session_id/turn_id或宿主不保留所需历史时暂停并报告，不能扩大批准范围。启用时完成宿主要求的原生审阅/信任，并以实际安全探针确认拦截；配置存在、enabled或trusted标签均不能代替运行证据。

### 初始化接入步骤

新项目初始化必须在首次服务器操作前完成下列接入；首次换宿主、注册入口或执行通道变化时只复核受影响部分，不能把CLI的验证结果直接沿用到桌面或其他通道。

1. **确定宿主和绑定**：从当前运行环境确认宿主及执行通道，不凭已安装某个CLI猜测。核对项目绝对路径、实际OPS_ROOT、Python 3.11+与PyYAML，以及上表所需的确认能力；Codex另核对本机CLI及原生会话历史可读性。资料或能力不明先核实，不安装无关软件或顺带配置其他宿主。
2. **启用前隔离自检**：在写入可能立即生效的Hook配置前，复用现有生成器和隔离输入检查配置可解析、项目/运维根绑定及allow/ask/deny/异常响应；命令只作为文本传给适配器，不执行真实服务器动作。准备并核对后续本地假SSH探针，其代码只能写本地标记，不得联网或执行传入的命令。自检失败先修复，不启用；已有Hook时使用下述维护入口，不临时停用现有保护来跑自检。
3. **生成并落地配置**：复用已自检的`--print-config`输出，将host替换为当前宿主；自定义OPS_ROOT追加`--operations-root <项目相对路径>`。AI先读取实际目标配置再合并，缺失时创建必要文件；以适配器入口、宿主及project-root识别本技能已有注册，相同内容不重复追加，变化时仅更新对应条目。保留其他Hook、事件、权限和设置，不为让验证通过而删除或放宽其他规则。JSON/TOML损坏或归属冲突先停止修改并核实，不覆盖整个文件。Kimi使用用户级文件时只添加绑定本项目的条目，保留其他项目配置并说明影响范围。将本地临时探针和使用标记所在`.local/`纳入Git忽略，保留原忽略规则。配置只引用共享适配器和项目策略，不复制权限表。
4. **完成宿主启用**：核对实际加载位置和启用状态。宿主要求人工审阅/信任时，先完成配置及差异展示，再请用户通过其原生入口完成；已有效且未变化的信任直接复用，不自写信任状态或绕过审阅。仅需本地骨架、尚无服务器资料时可完成配置准备，保持待验证，不虚构接入成功。
5. **验证当前通道**：启用后只通过当前宿主执行预先准备的本地安全探针，验证自动触发而非AI手动调用脚本；使用假SSH的绝对路径，不调用系统SSH或真实服务器操作。验证allow继续、ask确认后单次执行、取消/拒绝不执行、deny/异常阻止及重复答复不复用；当前策略缺少相应用例时使用隔离样例，不修改实际权限来凑测试。问询明确用于本地接入验证，不授予服务器操作权限；临时文件按全局规范放置并清理。代码单测、直接调用Hook成功或其他通道成功，均不能代替这一步，不在已启用的项目通道运行解释器自检。
6. **记录状态并继续**：在项目AGENTS既有工具/验证条目记当前宿主、入口、验证通道与覆盖范围；明细只关联本次execution.md。当前通道所需分支通过才记“已验证”；配置已写、尚待信任、仅模拟或部分验证记“待验证”；宿主无Hook或适配器缺少必要确认能力记“不支持完整接入”，说明具体缺口。后两者继续本地准备，暂停首次服务器操作，不自动退回仅靠AI主动判定，也不新建接入报告、状态JSON或批准文件。

后续维护时，配置查看与局部更新使用宿主文件工具；生成器和隔离测试在目标项目之外的可信技能仓库开发上下文运行，显式传入目标project-root及实际operations-root，并核对宿主实际cwd和平台权限。该入口只做本地技能维护，不执行服务器动作；不得关闭Hook、搬移服务器命令来规避检查或添加通用解释器白名单。更新注册后按需重新审阅，再验证目标项目的实际执行通道；无法使用合法维护入口时暂停并报告。

### 覆盖与失败边界

依赖Python 3.11+与PyYAML。固定project-root限定所属项目，工具cwd与原生会话cwd共用规范路径的归属判断；原生会话允许项目根及子目录，项目外或软链接逃逸时拒绝答复核验。项目外的工具调用不继承本项目许可，交回宿主自身权限。operations-root默认为agent-works/operations，自定义时须为项目内相对目录，拒绝绝对路径、上级跳转及软链接逃逸。从该目录的服务器清单与项目策略绑定精确地址、端口和账号。当前只支持显式`-F /dev/null`、严格主机核验、禁连接复用且末尾一个远端命令参数的非交互SSH；未知选项、代理、转发、脚本、解释器及组合语法停止，不猜测内层动作。连接策略中的语义禁止项、主机指纹及凭据核验仍由执行者先检查。

普通本地命令仍服从宿主原权限；任意可执行程序、文件工具、SQL/API及持续write_stdin输入未形成完整覆盖。不提供同账号防篡改或系统级隔离。脚本捕获的错误统一阻止，但宿主对脚本启动失败、超时或未覆盖路径可能继续执行；因此必须分别验证适配器和真实宿主。

协议与限制见[Codex Hooks](https://learn.chatgpt.com/docs/hooks)、[Claude Hooks](https://code.claude.com/docs/en/hooks)、[Kimi Hooks](https://moonshotai.github.io/kimi-code/en/customization/hooks)。验证覆盖allow继续、ask确实进入原生审批或明确阻止、deny/异常阻止、取消/拒绝不执行、目标与传输边界；模拟事件不能冒充真实客户端验收。Windows/PowerShell不属于当前支持的命令入口。

## 初始化、迁移与验证

初始化复制完整默认JSON，填精确目标和真实初始化请求来源，不另批默认基线。新增场景先判断哪类操作占多数，再选默认行为、只写反向例外，最后配置共同禁止项及测试；模式切换是权限变更，不能只换default而保留旧的相反例外表。

旧版顶层`default/allow/ask/deny`格式继续按原默认询问语义兼容，旧模式中的花括号不新增备选含义；新配置不再使用旧格式。已有项目不自动迁移，用户要求时才展示差异、取得覆盖相应放宽的批准、递增版本并整体切换，保留真实来源与有效限制。

配置验证覆盖两种模式：未命中例外时确实采用默认行为；命中时按反向例外决定；共同deny优先；规则与命令分别采用短/长/等号形式并加入显示参数时交叉同判；同一场景同时含allow/ask必须报错；重叠前缀只选一个；备选动词、参数变体、对象名rm/exec、未登记目标、草案及旧格式均有正反例。复用原判定器和测试，不另建平行权限系统。

```bash
python3 <技能目录>/scripts/check_command.py --policy <项目策略.json> --server-id <服务器ID> --user <账号> --command 'docker --host unix:///var/run/docker.sock service ls --filter name=portal'
```

输出decision/reason/pattern/policy_version，新格式另给scenario/mode；退出码allow=0、ask=2、deny=3。消费方须先检查reason：`invalid-policy`即使同为退出码2，也必须进入恢复策略的停止分支，不能进入普通ask的执行确认分支。判定器只分类文本，不连接、不执行、不验证批准或秘密，不提供系统级隔离；ask由主流程及宿主适配取得当次人工答复，分类结果本身不签发许可。
