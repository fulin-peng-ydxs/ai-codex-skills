# 前端审查清单

用于判断项目能否直接生成 `DESIGN.md`，以及是否需要先确认。

## 直接生成硬条件

必须同时满足以下条件，才可以直接生成或更新 `DESIGN.md`：

- 有明确前端目录和可识别页面结构
- 已确认样式入口、主题变量、token 文件或基础样式来源
- 阅读能代表本次范围的页面与组件；样本不足以支持全项目结论时缩小规范范围并说明依据
- 若项目包含后台台账、表格、筛选页、弹窗或抽屉，代表性页面中必须至少包含 1 个高密度界面页面
- 多数已阅读页面在颜色、字体、圆角、间距上基本一致
- 已定位本次适用的基础组件或稳定实现，不要求项目具备清单中的所有组件
- 能从代码或现有契约确认目标视口、布局策略与适用边界

项目规模很小时，可先说明依据不足，并给出最小规范建议。

## 需要先确认的信号

以下信号用于识别尚未授权的关键选择；已有明确授权覆盖时直接执行，不重复确认。多个风格或实现并存只有在同角色规则冲突时才构成收敛问题。

- 同类组件出现多套互相冲突的视觉实现
- 同一项目同时存在两种以上明显不同的风格体系
- 样式大量内联、零散、复制粘贴，难以抽象成稳定 token
- 几乎没有主题变量，颜色和尺寸定义到处散落
- 当前证据无法支持用户要求的规范范围，且需要决定是否扩大目标
- 需要在用户尚未授权的多个设计方向之间选择
- 已有 `DESIGN.md`，且新归纳结果会改变已有关键规范
- 高密度界面的空间、滚动或容器选择造成可观察的使用障碍，且收敛方案需要改变尚未授权的关键规范
- 主色、字体、圆角、间距或阴影体系存在多套冲突方案
- 页面风格明显不统一，无法判断应以哪部分为主
- 项目缺少关键规范，无法完整定义组件或布局规则
- 需要在多个候选方向之间做产品级选择，例如“保留旧后台风格”还是“收敛为新的统一风格”

## 建议补齐项

发现缺口时，可优先建议补齐：

- 颜色、字体、间距、圆角
- 基础组件规则：按钮、输入框、卡片、表格、弹窗、导航
- 响应式断点、容器宽度、页面留白
- 高密度界面规则：表格/列表空间利用、滚动层级、列宽分配、长文本处理、弹窗/抽屉/独立页面使用边界

高密度界面场景下，建议补齐项至少要落到可执行粒度：

- 列类型策略：哪些列窄、哪些列宽、哪些列固定、哪些列优先展示
- 长字段策略：省略、tooltip、两行截断、详情弹窗、展开行各在什么场景使用
- 操作列策略：可见动作数量、分组方式、是否固定及固定位置
- 滚动策略：页面滚动、表格滚动、弹窗正文滚动各自的边界
- 承载策略：普通 modal、宽 modal、drawer、全屏弹窗、独立页面的选择条件
- 桌面降级策略：在项目支持的最窄、典型和较宽视口下，哪些字段保留、截断、折叠或移入详情；不规定通用像素值

## 何时属于规范补齐

命中以下任一情况时，本次任务按“规范补齐”处理，而不是按“记录现状”处理：

- 固定小高度表格容器影响主内容区使用
- 页面、表格、弹窗或抽屉的滚动互相争抢，造成内容或操作不可达
- 列宽分配粗糙，关键字段难以判读
- 长文本处理方式导致行高失控或信息难以扫描
- 弹窗承载复杂表格、批量操作或长链路录入，导致必要信息或操作不可达

进入“规范补齐”后，必须：

- 明确指出当前实现中不宜直接固化为规范的部分
- 给出拟补齐的规范项
- 未获授权的关键选择确认后再写入；已有授权不重复确认

## 任务与能力规范覆盖

读取项目已确认规则与代表性实现，按本次范围选择以下能力。通用任务适用于桌面和移动端，原生输入、触摸与安装/缓存仅在项目使用时覆盖。缺口先区分局部记录项与尚需确认的产品决策。

| 方向 | 应能从规范中回答的问题 |
|---|---|
| 固定与滚动 | 页头、筛选、正文、操作栏、导航和弹层分别归谁滚动？哪些区域需要固定，哪些自然滚动？顶部/末端缓冲与整页越界如何区分？ |
| 可用空间与占位 | 固定操作与导航如何预留空间？最后一项可达、短内容无异常空白的判据是什么？涉及安全区和软键盘时如何适配？ |
| 控件与说明对齐 | 外框、文字内边距、帮助/错误文本、垂直中心各遵循哪种角色规则？原生日期/时间如何验证？数字编辑与列表比较是否各有明确约定？ |
| 密度与响应式 | 固定区占用后正文如何保持可用？长值、多条件和错误状态如何降级？如何减少视觉体量同时保留操作目标？ |
| 图表与瞬态提示 | 支持的输入方式各用什么读数入口？滚动、选择与下钻如何区分？离开或数据变化时哪些提示关闭、哪些选择保留？ |
| 用户文案与恢复 | 同类搜索与动作是否有统一名称？局部备份失败与正式操作失败如何区分？用户能理解结果并找到下一步吗？ |
| 共享能力 | 同类行为第二次出现时如何选择组件、状态 helper 或样式入口？已有与新增消费点如何共同接入，未抽取如何说明？ |
| 数字与导航恢复 | 展示精度、编辑中间态及语义色各以什么规则为准？首次进入、缓存返回、下钻返回和刷新分别恢复什么状态？ |
| 触摸与原生输入（涉及时） | 手势与替代入口、原生控件、软键盘往返和焦点交接的预期行为是什么？ |
| 安装与缓存（涉及时） | 安装态导航、离线、更新与恢复采用什么契约？ |
| 验证与事实源 | 关键规则是否有实现入口、适用状态和可观察判据？项目特有复测要求引用哪个入口？ |

尺寸、对齐方向、显隐时序、固定布局和图表策略只记录当前项目的稳定事实或已确认选择。实现机制与复测操作分别引用对应架构或验证入口，不在 DESIGN 再建第二份流程。

## 输出前检查

若本次 `DESIGN.md` 包含高密度界面规范，生成前至少确认：

- 已写明主数据区空间利用和滚动层级
- 已写明列类型策略和长字段处理方式
- 已写明操作列和动作承载方式
- 已写明弹窗 / 抽屉 / 独立页边界
- 已写明项目支持视口下的降级策略

按上表复核本次适用契约，能定位规则、实现入口与验证判据；不适用项说明边界，尚未确认的选择不能写成事实。证据结论使用 [前端验证范围与证据](../../page-ux-audit/references/verification-evidence.md)，待实施规则单独标注。

## 输出判断

- 满足全部硬条件且无确认信号：直接生成 `DESIGN.md`
- 满足全部硬条件，有局部缺口但不影响主体系：生成 `DESIGN.md`，并在 Known Gaps 或说明段标注
- 存在关键冲突或规范缺失：先给具体建议，按已有授权执行或确认未授权选择，再生成 `DESIGN.md`
- 几乎无前端依据：说明无法可靠生成完整 `DESIGN.md`，先建议补齐最小规范
