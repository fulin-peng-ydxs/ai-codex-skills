# Codex 全局 Skills 说明

这个目录存放当前用户自定义的 Codex 全局技能。每个技能使用独立目录管理，核心入口文件为 `SKILL.md`。

## 目录用途

- 作用范围：放在 `~/.codex/skills/` 下的技能，可在 Codex 会话中作为全局技能被发现和使用。
- 适用场景：沉淀可复用的工作流、固定交付格式、项目化规范、数据库/MCP 接入流程和自动化排障能力。
- 组织方式：一个技能一个目录；有补充模板、参考文档或脚本时，放在技能子目录内统一维护。

## 当前技能

以下列表只包含当前仓库中带有 `SKILL.md` 的用户自定义技能目录；`.system/`、`.git/`、`.idea/` 和未提供技能入口的辅助目录不计入“当前技能”。

按主要使用场景分为以下八类：

- [需求设计与开发交付](#需求设计与开发交付)：从需求闭环、正式需求到开发计划与开发留痕。
- [项目文档与架构治理](#项目文档与架构治理)：维护协作约束、README、设计规范、架构和项目接手文档。
- [审查与业务分析](#审查与业务分析)：检查代码质量、业务闭环、内存风险和自动开发提交，并还原已实现的业务流程。
- [系统资源诊断](#系统资源诊断)：分析磁盘空间和进程资源占用，辅助定位清理目标与卡顿来源。
- [前端设计与体验治理](#前端设计与体验治理)：覆盖视觉设计、UX、设计规范合规与前端复用。
- [自动化与工具集成](#自动化与工具集成)：管理 Codex 自动化以及跨工具、MCP 配置同步。
- [Git 协作](#git-协作)：生成提交消息并按授权完成提交与推送。
- [投资研究](#投资研究)：维护 AI 趋势知识源并分析上市公司。

| --- | --- | --- | --- |
| `auto-plan-dev` | 将已确认需求拆成可执行、可验证的开发任务。 | 在用户明确点名 `auto-plan-dev` 时，根据需求文档和 HTML 原型生成可执行开发计划；将性能与安全目标转换为独立技术方案，并闭环到实施任务、验证、发布回滚和剩余风险。 | 仅在用户明确点名本技能时使用；页面任务必须结合原型和 `DESIGN.md`。 |

| `requirement-doc-generator` | 将已确认闭环沉淀为正式、可验收的需求文档。 | 基于已确认的需求闭环和项目现状生成正式 `requirement.md`；独立说明可追溯、可验收的性能与安全目标，不越界指定开发实现；页面原型需在落地前确认，建议项需标明处理状态，写入前完成人工语义复核。 | 不越界指定开发实现；页面原型和关键建议项需先确认并标明处理状态。 |

| `code-reviewer` | 审查本地差异或远程 PR 的代码质量。 | 对本地改动或远程 PR 做代码审查，重点关注正确性、可维护性和规范一致性。 | 先明确审查范围；以可复现的正确性问题和项目规范为主要依据。 |

### 系统资源诊断

| --- | --- | --- | --- |
| `disk-usage-report` | 统计磁盘容量、目录占用并识别可安全清理目标。 | 分析当前电脑的磁盘使用情况，定位高占用目录和内容类型，评估可释放空间并给出分级清理建议。 | 默认只读分析；任何清理都要先列明完整路径、预计释放空间和风险，并取得用户明确确认。 |

## 使用方式

1. 在会话中直接描述需求，命中技能适用场景时，Codex 会按技能说明执行。
2. 如果想明确触发某个技能，可以在需求中直接点名技能名称或表达对应任务目标。
3. 使用前优先检查对应目录下的 `SKILL.md`，必要时补充 `references/`、模板或脚本资源。
4. 新增技能时，至少创建 `技能目录/SKILL.md`，写清名称、用途、触发条件、执行步骤和边界约束。
5. 如果技能要求显式触发，例如 `auto-plan-dev`，README 和 `SKILL.md` 都要同步写明“只有用户明确点名时才能使用”。
6. 需求类工作可先用 `requirement-closure-designer` 补齐闭环，再用 `requirement-doc-generator` 生成正式 `requirement.md`；两者职责不要混写，且“建议实现”都要明确处理状态，避免后续计划无法判断是否纳入。
7. 涉及页面需求时，`requirement-doc-generator` 负责判断是否创建 `prototypes/*.html` 并在落地前先做用户确认；原型里的交互元素必须与需求中的真实功能一致，禁用/暂不实现控件、说明批注和原型演示控件都要与正式业务界面明确分层，说明性内容不得伪装成正式页面内容，支持隐藏批注时这些辅助内容也要随之隐藏。需求文档中的建议实现和优化项也必须保留处理状态。
8. 需求文档只识别页面是否依赖已有通用前端能力、是否可能新增通用能力、是否涉及配置化承载；具体组件实现、注册、消费和验证任务由开发计划承担。
9. `auto-plan-dev` 读取这些原型作为计划拆解、页面实现映射和验证依据，不得跳过原型直接按泛化文字拆任务；涉及页面时还必须读取 `DESIGN.md` 和适用设计规范，将要求融合到对应页面的技术实现与验收内容；执行过程中更新计划时，必须同步补充任务的实际落地情况、各类测试/验证的具体完成情况，以及可选增强是否纳入或跳过的开发状态，不能只改状态。
10. 涉及运行时复用组件、布局、组件配置或页面注册能力时，`auto-plan-dev` 必须先识别项目现有接入机制和事实源：自动发现或自动继承时不新增重复登记，显式登记时只补齐本次实际涉及的契约，不存在相关平台能力时不新增配置体系；同时写清复用或新增判断、真实消费页面、必要的规范或资产清单维护及验证方式。
11. 性能与安全内容按阶段分工：`requirement-doc-generator` 负责独立说明与业务场景相关、可追溯且可验收的目标和边界，不提前指定实现；`auto-plan-dev` 负责将目标转换为独立技术方案并映射到任务、验证、发布回滚和剩余风险；`development-trace` 负责记录实际落点、真实验证、偏差和未解决风险。
12. 前端审查要按目标拆分：`page-ux-audit` 负责页面体验、交互直观性和控件必要性，`design-compliance-audit` 负责 `DESIGN.md` 等设计契约遵循，`frontend-reuse-enforcer` 负责重复实现、抽象边界和复用优先判断；不要把这三类问题混写成一个技能职责。
13. `business-feature-audit` 只负责业务闭环、状态流转、上下游协同和前端业务承接，不替代页面 UX、DESIGN 合规或前端复用治理；涉及这些问题时应转交对应前端审查技能。
14. 需要还原已实现的单个业务功能从入口、鉴权、筛数、写表、状态推进到终态的实际运行链路时，使用 `business-closed-loop-flow-analyzer`；尚未落地的目标流程交给 `requirement-closure-designer`，当前改动核查交给 `business-feature-audit`，整个模块或技术子系统说明交给 `module-architecture-doc-generator`。
15. 新建页面、落地页、仪表盘、组件视觉改造或其他需要显著提升界面辨识度的任务，可显式调用 `frontend-design` 获取更有个性的视觉方向、排版、配色、动效和文案指导；该技能聚焦设计表达，不替代业务闭环或代码复用审查。
16. 分析上市公司质量、估值、风险、评分或建仓情景时，可使用 `five-dim-stock-analysis`；完整分析必须先核对数据质量和最新官方报告，季报增量跟踪必须有可用的完整分析基线，证据不足的评分项和价格区间不得强行补值。
17. 涉及 Codex 自动化的创建、精简或排障时，优先使用 `automation-setup-assistant`；如果自动化依赖其他技能或项目文档，提示词应只补充固定目标、差异化约束和外部副作用边界，不要重复整段技能或项目规则。
18. 需要按 Git 提交范围审查近期 AI 自动开发结果时，使用 `agent-auto-commit-audit`；它负责串联代码审查、业务闭环核查、页面审查、必要修复和文档同步，不替代单独的技能开发或常规提交消息生成。
19. 涉及 Git 提交文案生成时，使用 `git-commit-msg`；它只输出提交消息，不执行 `git add`、`git commit` 或 `git push`。只有用户使用 `$git-commit-msg` 或明确要求调用该技能时才交互确认文件范围；被其它提交流程自动调用或普通生成请求时，由 AI 自行核定可靠范围并直接输出文案。
20. 需要实际执行 Git 提交与推送时，使用 `git-push`；只有用户使用 `$git-push` 或明确要求调用该技能时才执行文件范围、提交文案、staged 清单和 push 的交互确认；普通“提交”“推送”请求由 AI 按可靠范围连续执行，但不得扩大用户对 push 的授权。
21. 需要把 Codex 的全局 skills 或协作说明对齐到 Claude Code、Kimi Code 时，使用 `sync-codex-config`；它必须调用随技能提供的 `scripts/sync_codex_config.py`，默认先执行 `--dry-run` 预览，再按用户授权执行正式同步；Claude 目标文档写入 `CLAUDE.md`，Kimi 目标文档写入 `AGENTS.md`，不会删除目标端独有技能、文件或其他安装配置，并且要显式排除所有 MCP 相关技能。
22. 需要快速接手、盘点或评估整个项目及多仓交付包时，使用 `project-handover-analyzer`；它默认按稳定的 14 章骨架输出完整单文档，负责总体功能、运行与部署拓扑、跨模块依赖、交付完整性、典型调用链和接手路线。单个模块的详细架构继续使用 `module-architecture-doc-generator`，单项已实现业务闭环继续使用 `business-closed-loop-flow-analyzer`。
23. 使用 `module-architecture-doc-generator` 时，先读取 `references/output-contract.md`，按输出契约生成并逐篇运行 `scripts/validate_architecture_doc_structure.py`；用户或仓库要求其他结构时，说明例外并使用 `--custom-structure`，结构校验不能替代事实和内容完整性复核。
24. 排查磁盘空间或电脑卡顿时，分别使用 `disk-usage-report` 或 `process-usage-report`，默认只读采样并说明测量限制；实际清理前必须读取 [清理安全规则](disk-usage-report/references/cleanup-safety.md)，处理进程前重新核对目标身份与影响，并按技能要求取得明确授权。

## 编写建议

- 描述要聚焦“什么时候用、具体怎么做、哪些不能做”。
- 明确输出位置、交付要求、确认条件和安全边界；只有稳定对外接口、机器读取契约或用户明确要求固定的字段才做结构化强约束。
- 有固定模板或参考材料时，放进技能目录并在 `SKILL.md` 中显式引用。
- 技能面向复用，优先沉淀稳定流程，不把一次性上下文写进全局技能。
- 技能触发方式、关键资源、维护约束发生变化时，优先更新对应 `SKILL.md`，并同步检查本 README 的“当前技能”和使用说明是否仍准确。
- 新增、删除或重命名顶层技能目录时，优先同步“当前技能”列表；若新增技能改变了适用场景边界，也要补齐 README 中的用途说明和使用指引。
- 若 Git 提交流程类技能新增了稳定的确认节点、交互式提问工具依赖、staged 校验或 push 安全约束，也要同步检查 README 是否已准确反映职责分工。
- 若 Git 提交流程类技能调整显式调用、流程内自动调用或普通请求的交互边界，也要同步检查 README 是否准确区分各调用模式，且不改变用户对提交与推送的授权范围。
- 若业务闭环分析类技能调整稳定章节、数据权限运行链路、表关系、字段赋值或与需求闭环、业务核查、模块架构的职责边界，也要同步检查入口文件、关键参考资料和 README 的描述是否一致。
- 若新增跨工具同步类技能，README 需写清源目录、目标目录、是否先预览、是否覆盖文档、是否保留目标端独有文件，以及是否排除某类技能，避免把一次性复制流程误写成删除式镜像。
- 若公开数据投资分析类技能调整了评分口径、数据完整性门槛、来源优先级、季度基线、报告模板或采集脚本，必须同步核对入口文件、相关 `references/` 与脚本的约束一致性，并检查 README 的用途和使用边界。
- 若 MCP 同步类技能新增或调整启动参数同步规则、命令匹配优先级、配置块更新策略或报告脱敏要求，也要同步检查 README 是否已准确反映这些维护约束。
- 对以需求文档为输入的技能，若调整上游结论继承、模板、原型或验证方式，必须依据实际存在的资源同步检查入口与 README，明确职责和先后关系。
- 若需求闭环、需求文档或开发计划技能新增了稳定状态枚举、范围映射、原型约束、前端组件与配置接入闭环或是否纳入的约束，也要同步检查 README 是否已写清这些维护规则。
- 若 AI 约束文档、项目 README 或模块架构文档类技能新增了稳定的输出契约、结构校验、命令验证门禁、输出目录规则、薄入口职责分离或文档索引约束，必须同步核对技能入口、参考资料与校验脚本的一致性，并检查 README 是否已准确反映这些规则。
- 若项目接手分析类技能调整默认章节骨架、证据与完整性门禁、扫描分类或报告模板，必须同步核对入口文件、参考资料、模板、扫描脚本和测试的一致性，并检查 README 的用途与相邻技能边界。
