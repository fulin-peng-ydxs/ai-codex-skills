# 自动化任务配置助手

## 职责与边界

当用户希望创建、更新、验证或排查 Codex 自动化任务时，使用此技能。

本文维护自动化配置、诊断、提示词分工与验证流程；实际配置字段和可用操作以当前自动化工具 schema 为准，业务细则由被调用技能与项目规范维护。

## 输入与前置条件

先检查当前环境的 automation_update 工具和已有自动化配置，确定新建、更新或只诊断；已有任务优先更新，避免重复创建。

### 入口判断

- 如果用户要新建自动化或修改已有自动化，走“创建流程”。
- 如果用户说自动化失败、没有权限、没有运行、结果不对，或要求查看执行记录，走“诊断流程”。
- 当用户使用中文沟通时，自动化名称、提示词、状态汇报和最终结果都优先使用中文。

## 执行流程

### 创建流程

1. 依据用户目标选择类型：周期性跟进默认使用当前线程的 `heartbeat`；仅在用户明确要求每次创建独立任务或独立项目作业时使用 `cron`。cron 通过项目列表取得单个 `projectId`，具体字段以工具 schema 为准。
2. 只收集缺失的必要输入：
   - 任务目标。
   - 运行时间、频率或触发条件。
   - 目标路径、仓库、URL、服务或线程上下文。
   - 需要的能力，例如文件写入、Git、网络、数据库、浏览器或凭据。
   - 结果汇报方式和失败处理方式。
3. 创建自动化前做本地预检查：
   - 检查目标路径是否存在。
   - Git 任务需要确认每个路径都是仓库，并查看 `git status`。
   - 检查引用到的技能、脚本、配置文件或凭据是否存在。
   - 识别可能需要授权的命令，尤其是带网络访问的 `git push`。
4. 使用 当前可用的 `automation_update` 工具 创建或更新自动化。
   - 更新时保留用户未要求改变的字段，并传入既有 ID 和完整更新字段。
   - 静音使用工具的 `notificationPolicy=failed_runs_only`，取消静音使用 `null`，不把通知设置写入提示词。
   - 持续监测默认在状态无变化或无可行动事项时保持安静，仅在有意义的变化、完成、失败或需要用户处理时通知；用户明确要求定期汇报时遵从其要求。
   - 按“提示词职责边界”编写提示词。
   - 如果命令授权很重要，必须要求使用稳定的显式命令，例如 `git -C /path/to/repo push`。
   - 用户明确要求独立的多仓库作业时，每个 cron 绑定一个项目；检查重复任务和并发提交风险，不构造工具不支持的多个 cwd 字段。
5. 创建后做验证：
   - 查看自动化配置。
   - 本地运行安全的预检查命令。
   - 对网络、push、发信、外部 API、写库等高风险工作流，按用户授权和工具规则验证一次关键链路。
   - 能安全手动运行自动化时，手动运行并检查 `~/.codex/automations/<id>/memory.md`；如果会发送消息、推送、写库或长时间执行，说明未手动运行的原因。
   - 如果手动运行失败，必须根据运行记录在授权范围内修正自动化提示词、项目绑定或权限策略；只在当前线程验证同名命令不算完整验证。

### 诊断流程

1. 定位自动化：
   - 如果用户没有提供自动化 ID 或名称，检查 `~/.codex/automations/*/automation.toml`。
   - 如果已知 ID，使用 当前可用的 `automation_update` 工具 的 `mode: view` 查看配置。
2. 查看运行记录：
   - 如果存在 `~/.codex/automations/<id>/memory.md`，优先读取。
   - 在 `~/.codex/logs_2.sqlite` 中搜索自动化 ID、名称、目标路径和错误关键字。
   - 如果 SQLite 日志上下文不足，再查看 `~/.codex/log/codex-tui.log`。
3. 归类失败原因：
   - 文件系统权限或沙箱写入限制。
   - Git 仓库状态问题。
   - 网络或 DNS 限制。
   - Git 远端凭据失败。
   - 缺少依赖、文件、技能或脚本。
   - 自动化提示词不够明确，导致选择的命令没有命中已授权规则。
   - 多个 cwd 触发多次运行，导致同一仓库并发提交或 `.git/index.lock` 冲突。
4. 用户要求修复时，在已授权范围内处理；只诊断时交付原因和建议：
   - 更新自动化提示词，改用稳定的显式命令。
   - 网络与写入按当前工具权限和已有授权处理；不重复索要有效授权，也不在禁止升级的环境申请升级。
   - 持久权限调整须有明确授权且当前环境支持，规则限定到必要的精确命令。
   - 对需要用户凭据、外部服务访问或手动 App 设置的阻塞点，明确说明。

## 核心约束

### 提示词职责边界

自动化任务需要生成文档时，引用 [文档结构与输出规范](~/ai-agent-config/config/force/document-output.md) 和对应业务技能的输出契约；自动化提示词只补充任务差异，不复制模板，也不把固定字段改成可选。

自动化提示词必须能让后台任务独立运行，但不要复制被调用技能、项目文档或外部规范的完整细则。

必须写入自动化提示词：

- 固定目标：项目路径、仓库、URL、线程、收件人或服务名。
- 调度目标：这次自动化要完成什么、何时算成功、失败如何汇报。
- 工具和资源入口：需要读取的技能、脚本、配置、项目文档和凭据来源。
- 与默认技能不同的差异化约束，例如“只本地 commit 不 push”“邮件必须包含提交 hash”。
- 安全边界：不能处理的路径、不能提交的文件、需要用户授权的命令或外部动作。
- 最终汇报方式：发到哪里、正文必须包含哪些机器可读或业务关键结果。

不要在自动化提示词中重复：

- 被调用技能已经定义的审查清单、输出章节、测试矩阵或业务细则。
- 项目 `AGENTS.md`、`DESIGN.md`、`README.md` 中已有的稳定规则全文。
- 大段示例、历史背景、创建原因和临时解释。

当自动化依赖某个技能时，提示词用短句要求“读取并遵守该技能”，再补充本自动化特有的覆盖规则。只有安全红线、外部副作用和机器读取契约需要在提示词中重复。

### Codex 自动化网络处理

当自动化需要访问网络时：

1. 不擅自改成系统级 `launchd`、`cron` 等外部定时任务，除非用户明确要求换方案。
2. 根据自动化自身日志区分 DNS、主机网络、沙箱、凭据和远端错误；DNS 失败本身不能证明是沙箱限制。当前聊天成功不代表后台线程成功。
3. 使用精确稳定命令，例如 `git -C <已授权仓库绝对路径> push`。只有当前工具支持权限升级、环境允许且授权适用时，才通过对应机制重试同一命令；禁止升级或缺少能力时报告阻塞，不绕过权限。
4. 持久允许规则须由用户明确授权，并使用环境支持的配置入口；不默认改写 `default.rules`，不加入宽泛的 `git` 或 `git push` 规则。
5. 修复后在授权和工具能力允许时运行自动化本身并核对结果；无法实际运行时报告未验证，不把配置保存或当前线程成功当作后台闭环成功。

## 产出边界与交付

交付自动化名称、实际配置变更、运行状态、验证证据和阻塞项。仅诊断时不擅自修改调度、权限或任务内容；创建与更新不自动授权消息发送、推送或写库。

### Git 目录监测示例

如果需要参考“监测本地技能目录并每晚自动提交变更”的完整示例，读取 `references/git-directory-monitor.md`。

## 验证与完成标准

分别核对配置保存、安全预检查和自动化自身运行结果；只在当前聊天运行同名命令不能证明后台任务成功。未执行或缺少能力时说明限制，不能报完整链路通过。
