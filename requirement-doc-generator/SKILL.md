# 需求文档生成器

## 核心目标与资源路由

将用户的初步想法整理成能指导开发计划和测试设计的 `requirement.md`，以项目事实和已确认业务闭环为依据，不输出泛化 PRD，也不越界替代技术设计。

按任务阶段读取资源：

- 开始执行时完整读取 `references/artifact-consistency-contract.md`，遵守事实层级、闭环交接、范围、状态、字段和需求/设计边界。
- 创建、更新或检查最终文档结构时，完整读取 `references/requirement-template.md`。
- 涉及页面、交互或 HTML 原型时，完整读取 `references/prototype-rules.md`；纯后端或无页面需求不读取。
- 交付前运行 `scripts/validate_requirement_artifacts.py`；脚本只检查结构，业务语义仍需人工复核。

## 执行流程

### 1. 确定项目与输出位置

- 输出到目标项目的 `./agent-works/{feature-slug}/requirement.md`；用户指定路径时优先使用。
- `{feature-slug}` 使用稳定业务语义和 kebab-case；同一功能已有目录时优先复用。
- 当前工作区不是目标项目，或缺少用户要求结合的项目上下文时，先确认项目路径。
- 目标文件已存在且用户未明确要求更新时不要覆盖；能判断为不同功能时使用更精确的 slug，同一功能但更新意图不明时先确认。

### 2. 继承上游闭环

- 已有需求闭环分析或 `requirement-closure.md` 时，将其作为主要输入，不重新发散另一套业务闭环。
- 继承已确认的功能点、范围、页面入口与职责、角色、状态、数据变化、权限、异常反馈和确认结论。
- 存在 `CL-xx` 交接键时，先建立“闭环键 → R 编号 → 范围状态 → 承载章节 → 验收位置”映射，并保证全部交接键有去向。
- 历史闭环文档没有 `CL-xx` 时，更新闭环文档应补齐交接键；只更新需求文档且未获授权修改闭环文档时，按功能语义继承，并在校验时使用 `--allow-legacy-closure` 保留迁移警告。
- 下游发现冲突时，区分“项目事实冲突修正”“必要细化”和“新增建议”；新增建议不得静默进入必须实现范围。
- 用户只提供闭环结果但未要求生成正式需求文档时，不自动写入 `requirement.md`。

### 3. 调研项目事实

- 阅读相关业务流程、代码、页面、接口、服务、数据结构、权限、配置和测试；有可用数据库信息时结合真实结构与数据。
- 记录能影响需求的项目依据和访问限制；无法验证的内容不写成事实。
- 以当前项目业务专家和资深架构视角校验术语、规则、闭环和落地可行性，但不把内部实现自动升级为需求。

### 4. 补全需求与边界

- 按相关性补齐角色、入口、主链路、关键支链路、状态、权限、数据口径、配置、异常、恢复、回退和可观察结果。
- 结合实际需求检查增删改查、查询筛选、导入导出、空/错/加载状态、数据一致性、并发、数据量、安全和兼容性；不相关内容不机械扩写。
- 涉及状态、部分失败或新增字段时，按共享契约分别完成状态闭环、部分失败闭环和字段闭环。
- 只冻结项目稳定契约、会改变业务语义或验收结果的约束、用户确认的不可后置方案，以及必须确定的对外接口、存储语义或跨系统协议。
- 类名、私有方法、文件改动、内部算法、索引实现、事务实现和任务拆分默认留给技术设计或开发计划。

### 5. 处理页面、原型与配置化

- 涉及页面时先读取 `references/prototype-rules.md`，检查项目 DESIGN、组件、模板、布局、注册和配置能力。
- 新增页面生成并引用 `prototypes/{page-slug}.html`；既有页面按变更复杂度决定是否生成原型。
- 原型只澄清页面承载和关键交互语义，不验证生产级算法、完整数据或实现质量。
- 配置化需求写清定义、展示、保存、读取、消费、校验、默认值、非法值、失效和回退；多页面复用时明确基础能力范围，不指定内部实现。

### 6. 分类不确定项

- **阻塞确认**：答案会改变业务流程、数据结构、权限、状态、集成契约、范围或验收；解决前不生成最终文档。
- **非阻塞确认**：不影响开发计划启动，只影响默认值、次要交互、提示或复杂度；询问用户是否确认，未确认则记录遗留项或形成有依据的推断决策。
- **自行推断**：有项目惯例、低风险、可回滚且不改变闭环；直接记录结论和依据。
- 上游已有结论时默认继承，只有事实变化或新增约束导致失效时才重新确认。

### 7. 冻结范围与编号

- 范围只分为必须实现、建议实现和暂不实现，同一功能只能属于一个类型。
- 建议实现状态只使用 `本次纳入`、`后续建议`、`已实现`、`待确认`、`不纳入`，有效范围按共享契约判断。
- 范围和功能语义冻结后再分配稳定 R 编号；一个编号只表达一个可独立验收的需求，不复用、不变义。
- 所有编号都能追溯到用户诉求、`CL-xx`、项目事实、推断决策或新增建议。
- 本期需求在功能范围、详细需求、数据/页面承载和验收标准中保持同一编号与语义。

### 8. 确认并写入最终产物

- 阻塞项解决后，读取 `references/requirement-template.md` 组织最终文档。
- 用户只要求草案时，在对话中输出摘要或待确认清单，不把草案当作最终文件写入。
- 涉及页面时，写入前先向用户展示输出目录、页面与原型清单、关键布局假设和剩余确认项；用户确认后再创建或覆盖文档和原型。
- 区分已确认事实、项目依据、推断决策、风险和遗留确认项；没有遗留项时删除对应章节。
- 更新既有需求文档时保留稳定编号，并按真实确认或实施结果同步处理状态。
- 建议实现和优化建议均保留处理状态；暂不实现项说明原因和未来触发条件。
- 保留建议开发顺序：小需求说明单阶段完成，大需求按依赖、页面承载关系和可验证里程碑分阶段，不写工时、人员或开发任务清单。

### 9. 执行交付门禁

- 运行：

  ```bash
  python ~/.codex/skills/requirement-doc-generator/scripts/validate_requirement_artifacts.py \
    --requirement <requirement.md> \
    [--closure <requirement-closure.md>] \
    [--research <research.md>] \
    [--allow-legacy-closure]
  ```

- 修复脚本错误，逐项判断警告，并人工复核脚本无法判断的状态、权限、数据口径、失败语义和页面承载关系。

## 交付标准

- 上游交接、范围和需求编号追溯完整，无平行需求或静默扩项。
- 每个本期需求都有足够的详细定义、相应的数据/接口/页面/流程承载和可验证验收。
- 无未解决阻塞项；事实、推断、风险和遗留项边界清楚。
- 文档停留在需求层，原型停留在澄清层，开发顺序不退化为开发计划。
- 自动结构校验通过，并完成人工语义复核。
