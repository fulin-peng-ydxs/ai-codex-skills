# 需求闭环设计器

## 职责与入口

维护需求在系统中如何跑通：功能链路、角色、状态、范围和未决事项。正式编号及验收契约由需求文档维护，实施拆分由开发计划维护；保存时把此边界补入已有用途说明，不重排成果。

执行前读取 [需求协作共用契约](../requirement-doc-generator/references/workflow-contract.md)，继承调研、确认、保存和自适应规则；无需读取正式需求技能全文。

## 操作选择

| 用户意图 | 执行动作 |
| --- | --- |
| 首次分析、继续细化闭环 | 先在对话中完整分析，列出范围、依据和未决项；没有保存请求时不建目录或文件。 |
| 明确确认闭环无问题、可落地，或要求保存 | 保存所指当前成果，默认文件名 `requirement-closure.md`；路径可确定就直接执行，草案与未决状态如实保留。仅认可方向不视为完整闭环获批。 |
| 局部修改、重构 | 按共用契约维护当前基线，仅在获准范围改变内容或结构。 |
| 明确要求正式需求文档、PRD 或 requirement.md | 切换到 [requirement-doc-generator](../requirement-doc-generator/SKILL.md)，继承已有结论。 |

闭环阶段不分配正式需求编号，不自动生成 `requirement.md`、`prototypes/`、正式验收表或开发计划，也不提前展开性能、安全、兼容性专章。会影响业务成立的容量、安全或兼容边界仍须讨论，不能因不设专章而遗漏。

用户同时要求技术方案等复合成果时，首次输出分区承载，保存时完整保留；业务闭环部分只确定必要行为、边界和外部契约，类、函数、索引与内部事务编排留在技术方案部分，不升级为业务要求。

## 分析与最低内容

先调研可验证事实，再补齐下列适用信息：

- **目标与范围**：解决什么问题，必须实现、建议实现、暂不实现分别是什么；建议项沿用共用状态与互斥规则。
- **角色与入口**：谁能用，从哪里进入，前置条件、权限和配置如何影响操作。
- **完整链路**：主链路、关键支链路、操作与反馈、状态变化、结果保存和生效、交接对象、失败位置、继续或回退方式，以及怎样判断闭环成立。
- **功能清单**：各项的目标、入口、关键操作、反馈、状态、权限/配置、异常；可引用链路，避免重新抄写。
- **页面承载**：涉及页面、弹窗、抽屉或配置入口时，明确各自职责、跳转/联动/回流、数据变化、空态和失败反馈；只有影响闭环才展开接口、数据或上下游机制。
- **结论与未决**：项目事实、已确认结论、推断依据、阻塞与非阻塞项可区分；每个问题说明影响和需要决定的差异。

页面阶段不提前细化字段顺序、按钮位置、列宽、样式和微文案；但影响业务成立的入口、操作、权限和反馈不能留待 PRD 才补。

## 首次输出默认模板

首次完整分析默认使用以下骨架，按共用契约合并相近章节或裁剪不适用内容；每个功能点仍须独立可辨识。保存已有成果不重套模板。下方字段的语义要求见“分析与最低内容”，页面部分只补职责、衔接及页面特有信息，不重抄功能流程。

## 3. 用户角色、权限与使用场景

- 闭环成立的判断：

### 功能点：名称
- 目标与页面/入口：
- 前置条件、关键操作与系统反馈：

功能点使用业务名称追溯，不因套用模板分配正式需求编号；后续建议不自动触发下一阶段。

## 交付检查

- 按一条代表性场景核对操作、反馈、结果、交接和失败恢复；不能只复述用户诉求或靠章节齐全证明闭环。
- 范围不交叉，建议有状态，关键前提未知时不伪装成已闭环；生成成果按用户目标检查，保存成果按原基线检查。
- 保存后报告路径、新建或更新及遗留项，结束本次授权工作，不顺带生成正式需求、原型或计划。
