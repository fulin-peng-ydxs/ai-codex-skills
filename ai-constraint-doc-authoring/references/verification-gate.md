# 验证门禁

本文维护项目命令的执行验证、失败处理与受限例外，供约束文档和 README 技能共用；各调用方负责来源选择、文件维护授权和交付编排。本门禁不决定是否补建某类入口。

## 门禁原则

默认情况下，某条命令作为“必须执行的日常流程”写入 `AGENTS.md` 或其明确指向的项目权威命令正文前，必须在本次任务中实际成功执行；`CLAUDE.md` 按薄入口契约引用，不复制命令。非零退出、缺少工具、健康检查失败或超时都视为门禁失败。README 直接消费完整有效的命令来源不触发重验；需要补齐、更新来源或验证获准替代来源中的命令时，仍复用本门禁。

门禁失败时先按下方“失败处理”继续有依据的排障；正常落地须通过必要门禁。确有前置受限情况时，按“前置受限与例外确认”提出具体方案，取得覆盖本次范围的明确批准后才能采用例外，不因失败自行跳过。

验证范围以本次维护对象为准：仅维护规则和事实导航时，验证来源、授权边界、引用及文档结构，不因引用操作手册就执行其全部命令。新增或修改命令、执行条件或验证状态时，仍执行对应命令门禁；首次生成或整体重构代码项目入口，不能以“仅规则/导航”为由遗漏适用的项目命令。示例、归档或外部材料中的技术栈不自动属于当前可运行项目。尚未获准或无法验证的操作保留未验证状态及限制，不列为可直接执行的已验证流程；文档编写不扩大执行权限。

## 必备验证计划

编辑文件前先形成与本次维护对象对应的验证计划；有待维护的命令时，至少包含：

- `stack`：检测到的语言、框架或组件。
- `source`：证明命令相关的清单文件、脚本、README 章节或已有说明文件。
- `command`：精确命令和工作目录。
- `purpose`：环境、依赖、测试、构建、本地启动、健康检查、状态检查、停止清理或领域 CLI。
- `required_for_landing`：是否属于落地必验命令。
- `success_condition`：退出码、预期输出、监听端口、HTTP 状态、生成产物或测试结果。
- `cleanup`：若命令会启动服务，写清停止命令或进程清理方式。

遇到破坏性、生产环境、耗时昂贵、需要凭证、写外部服务或可能长时间运行的命令，先核对已有授权是否覆盖具体目标、动作及影响；未覆盖时按 [全局确认机制](~/ai-agent-config/config/force/collaboration-rule.md#需要先确认时) 请求决定，已覆盖时不重复索权。平台执行权限另按其原生机制核对。

## 必须通过的内容

至少验证所有将写入文档的常规工作流命令：

- 环境：运行时版本和包管理器版本。
- 依赖：仓库安全允许的安装或依赖可用性检查。
- 测试：每个检测到的技术栈的主测试命令，除非项目没有测试或用户明确只要求命令发现。
- 构建：每个可构建技术栈的生产或打包构建命令。
- 本地启动：文档会写启动流程时，验证启动、状态或健康检查、停止命令。

如果仓库提供封装脚本，优先验证封装脚本接口，而不是裸跑底层长期命令。

## 长期服务

验证本地启动命令时：

1. 有状态命令时先检查当前状态。
2. 仓库有自动化专用端口时，不抢占用户日常开发端口。
3. 服务只启动到足够验证就绪。
4. 用状态命令、监听端口、HTTP 响应或健康检查验证就绪。
5. 只停止本次验证启动的进程；仓库生命周期规则另有要求时按仓库规则恢复。
6. 仓库要求恢复测试前状态时，按测试前状态恢复。

## 失败处理

命令失败时：

1. 记录命令、工作目录、退出状态和最短有效错误片段。
2. 将失败归类为缺少依赖、运行时版本不匹配、测试失败、构建失败、端口冲突、外部服务缺失、密钥缺失、数据锁、超时或未知。
3. 有新证据支持明确、安全且在既有授权内的修复时，自主修复并定向重试，例如恢复已声明依赖、改用仓库封装脚本、使用已核实的本地配置或清理由本 Agent 启动的进程。每次说明新依据及预期消除的问题；后续发现另一项独立原因时继续按同一判据处理，不设一次重试上限。
4. 相同失败重复且没有新证据时停止重复执行，可继续有目的的只读诊断；不能通过猜参数、换命令变体、弱化断言或跳过检查获取通过。确有已证实的命令/测试错误时，按授权修正并验证，不能掩盖真实产品缺陷。
5. 需要用户提供凭据或外部条件、修复超出授权、有实质方案选择，或继续诊断已无法取得有效依据时，报告具体阻塞、已完成检查和可审阅的处理选项；只暂停依赖部分，按下节请求决定，不因第一次重试失败笼统询问。

## 前置受限与例外确认

本节只处理无法按正常前置完成的情况，例如缺少运行环境/凭据、已定位的既有测试或构建故障、验证需要未获授权的外部写入，或验证成本明显超出本次文档任务范围。先完成可安全推进的调研和修复；不得仅为省事主动降级。

1. 展示具体命令及来源、工作目录、已执行结果或未执行原因、拟写入文件与内容、影响及剩余风险。区分来源缺失、实际失败和未执行，不把三者混成“无法验证”。
2. 提供适用选择及推荐：补齐条件后继续验证；采用已核实且匹配版本/环境的替代证据；或仅交付已验证部分，将受限命令保留为明确的失败/待验证说明及后续入口。需要变更来源时由调用方按其来源规则一并说明，不重复确认。正常路径可行时优先恢复验证。
3. 按 [全局确认机制](~/ai-agent-config/config/force/collaboration-rule.md#需要先确认时) 取得覆盖具体文件、命令、替代依据和交付限制的批准；已有精确覆盖的授权直接复用。未答、拒绝或范围不清时不落地依赖该例外的内容，可在对话交付草案；另写草案文件须有相应保存授权。
4. 获准后只在批准范围落地，在产物适用位置及交付说明中保留证据状态、限制和补验入口。替代执行证据注明来源、版本/环境及覆盖范围，不能称为本次本地执行；仍失败或缺少有效执行证据的命令不得列为已验证或要求直接执行的日常流程，也不因获批变为可用。

例外批准只改变约定的文档交付范围或证据方式，不放宽平台权限、安全边界，不证明失败已修复。必要前置通过与获准例外交付分别报告；未获例外且门禁仍失败时不覆盖正式入口。

## 汇报证据

交付或报告阻塞时汇报：

- 写入的文件。
- 按技术栈分组的已验证命令。
- 失败、待验证及未写入的命令、原因和后续入口；适用例外的批准范围、来源与交付限制。
- 残余风险，例如本地检查未覆盖的外部服务。
