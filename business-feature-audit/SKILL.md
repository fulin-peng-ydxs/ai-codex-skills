# 业务功能闭环核查

## 职责与边界

判断本次改动放回完整业务链路后是否成立，以业务功能为核查单位，代码缺陷作为业务影响的证据。只做核查及获准的报告维护，不修改业务代码。

参考：[文档编写规范](~/ai-agent-config/config/force/document-output.md) · [协作与目录规则](~/ai-agent-config/config/force/collaboration-rule.md)。具体检查项见 [核查维度](references/audit-dimensions.md)，正式产物见 [报告模板](references/report-template.md)。

## 输入与前置条件

### 模块边界

用户指定模块时以该模块为边界；未指定时结合会话、本次 diff、调用链和项目文档识别链路及文件范围。目录名、类名只能作线索；名称不明确但目标链路可定位时可以继续。范围须注明来自用户指定、项目证据还是待核实，不把分析结果写成用户确认。

默认对话核查（快速核查），不创建或修改报告及其他阶段文档。明确要求生成、保存或更新报告时进入正式产档；仅保存保留所指基线、有效修正与证据状态，不重新调研，局部更新只复核受影响部分。

### 信息来源

优先读取用户目标与说明、会话实际改动、工作区与暂存差异，再查相关需求、计划、已有 `agent-works` 文档及入口、服务、数据、页面、任务和消息等上下游代码。证据强度按每条结论分别标注：

- `confirmed`：已查看代码、diff、文档或用户说明能直接支持该结论；不据此推定线上行为。
- `inferred`：从调用关系、命名或相邻实现推断，写明推断依据。
- `missing`：缺少业务规则、配置、历史数据、外部契约或运行证据，说明不能判断的部分。

用户说明、需求与实现冲突时分别记录规则和代码表现；按证据判断为已确认偏差或待决问题，不强行合并。不输出敏感配置值，只记录位置、用途和环境差异。

## 执行流程

1. **定位本次范围**：核对项目、会话、`git status --short`、`git diff` 和 `git diff --staged`，识别业务文件，排除构建产物、依赖、临时及无关文件；按下述确认流程处理实质歧义。
2. **按功能分组**：优先沿用户验收项或需求功能点，再按独立业务目标、状态闭环、入口和下游影响分组。共同完成一个目标的文件合并；统计、消息等旁路作为其链路环节。具备独立入口、闭环或验收标准的能力分别核查，不按文件逐个点评。
3. **追踪链路**：关联需求、计划和已有报告，逐功能串联入口、处理、状态与数据、输出消费方、异常补偿和运营接管，检查本次影响到的旁路。
4. **判断问题**：读取核查维度，区分已核查、不适用和证据不足；按问题类别、证据强度和影响定级，给出可定位证据及复验条件。
5. **交付**：对话给出结论、已确认问题、待决问题、盲区和下一步。已授权产档且目标明确时，完整读取报告模板后写入，汇报文件、覆盖功能及验证限制。

### 确认流程

范围可由用户指向、会话和项目证据确定时直接继续；已要求产档即可按指定路径或同范围已有报告写入，常规标题、功能拆分及目录选择不另设审批。

只有核查对象无法确定、多个候选会实质改变结论、拟扩大范围、覆盖对象归属不明或写入超出授权时，先展示候选、证据、影响和推荐，确认未决部分；其他调研继续。业务规则或运行证据缺失可在获准报告中保留待决，不阻塞整份报告，也不将未答复视为批准。

写入前核对具体模块、文件范围及排除项、功能标题与拆分依据、已有需求/计划/报告和新建或更新路径；依据放报告适用位置，不建立额外审批清单。

## 核心约束

### 问题分类与严重级别

| 类别 | 判定要求 |
| --- | --- |
| 已确认问题 | 有直接证据及明确业务影响，通常必须具备 `confirmed` 证据。 |
| 待业务确认问题 | 是否构成问题取决于业务规则、外部契约或部署约束；写清待决定规则及现有 `confirmed` 或 `inferred` 证据。 |
| 暂无法确认的风险点 | 证据不足，通常为 `missing`；说明缺项、影响和补证方法。 |

严重级别表达影响，与问题类别、证据强度独立：`high` 为闭环断裂、关键状态错误、严重数据不一致、权限失控或上线后高概率故障；`medium` 为条件性遗漏、兼容风险或影响可控的问题；`low` 为局部轻微问题或完整性改进。潜在影响须标明，不能把推断或缺证写成已发生事实。

问题绑定业务链路位置及受影响角色、数据或消费方。页面只核查业务入口、权限、状态和反馈承接；排版与交互体验、DESIGN 遵循、重复实现分别由 `frontend-ux-audit`、`design-compliance-audit`、`frontend-reuse-governance` 处理。

## 产出边界与交付

正式产档默认文件名 `business-audit.md`，目录按协作规则确定，标题使用中文业务功能名称。同范围已有报告优先更新，不创建平行版本；保留有效背景、历史内容和证据，修正失效结论，归档按协作规则处理。

报告模板维护结构、稳定问题编号和处理状态；需求、架构和实施过程只保留本次判断需要的摘要及引用。未发现明显问题也须说明覆盖与盲区；建议不等于已实施，静态确认不等于联调或线上验证。

## 验证与完成标准

逐功能走读入口、状态、权限、上下游和异常恢复；逐问题核对证据→触发→影响→处理→复验，确保类别、严重级别、证据强度和实际状态一致。汇总引用详情，修复与复验分别有依据。

正式报告首次生成或整体重构后运行 `python3 <skills-root>/skill-authoring-standard/scripts/validate_document_template.py <产物路径> --template <本技能目录>/references/report-template.md`，并按模板核对内容。保存与局部更新保留基线；说明实际验证及未覆盖范围，不以格式通过代替业务核查。
