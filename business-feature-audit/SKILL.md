# 业务功能闭环核查

## 职责与边界

对本次开发涉及的代码做业务闭环核查。目标不是重复做普通代码审查，而是判断这次改动放回业务模块和完整链路后，整体功能是否成立，是否有未充分考虑的问题。

本文维护模式、范围、确认与证据规则；具体核查维度在 [核查清单](references/audit-dimensions.md) 维护；报告按权威模板编写，正式产档时读取 [报告模板](references/report-template.md)。

### 适用范围

在以下场景使用本技能：

- 用户要求核查“这次开发对应的整个业务功能是否合理”。
- 用户要求检查本次改动在某个具体业务模块中的完整性、闭环性和遗漏风险。
- 用户要求根据当前改动输出业务风险结论。
- 用户要求输出业务功能核查文档，而不是只做代码层面的 review。

本技能只做业务核查和业务核查文档生成，不修改业务代码。

## 输入与前置条件

### 工作模式

根据用户意图选择一种模式：

#### 快速核查模式

适用于用户只要求“看看这个业务功能有没有问题”“核查本次改动是否闭环”“这个技能有没有风险结论”等场景。

按 [模块边界](#模块边界) 识别范围，在对话中输出初步业务风险结论、证据、疑点和待确认问题，不创建或修改报告及其他 `agent-works` 文档。是否需要澄清及暂停按 [确认流程](#确认流程) 判断。

#### 正式产档模式

适用于用户明确要求“生成业务核查文档”“输出到 agent-works”“更新 business-audit.md”等场景。

按 [模块边界](#模块边界) 识别范围，使用报告模板交付；写入与暂停条件统一按 [确认流程](#确认流程) 判断。

### 模块边界

可接受示例：

- 隐患排查模块
- 隐患整改模块
- 告警处置模块
- 风险分级管控模块
- 双重预防大屏统计模块

范围识别标准（两种模式共用）：

- 用户已明确模块时，以用户模块为边界。
- 用户未明确模块时，综合会话、diff、调用链和项目文档界定业务链路与文件范围，标明依据；区分用户指定、证据识别及仍待核实，不把分析结果写成用户确认。
- 仅目录名或类名只能作为线索，不能单独证明业务归属。名称不明确但目标改动及业务链路可定位时，范围仍可确定；存在多个候选时记录各自证据、缺口及对边界和结论的影响。
- 本节只判定范围及其证据是否充分，写入授权与业务规则确认不能由范围识别替代；下一动作按 [确认流程](#确认流程) 执行。

### 信息来源

按以下顺序收集证据，结论必须能从证据中推导，并标明证据强度：

1. 用户在当前会话中明确给出的业务模块、核查目标和补充说明。
2. 当前会话中实际新增或修改的业务文件。
3. Git 工作区改动：`git status --short`、`git diff --stat`、必要时查看具体 `git diff -- <file>`。
4. 项目已有需求、开发计划和 `agent-works` 文档：优先查找项目内 `./agent-works/`，必要时再查找工作目录中的相关计划。
5. 与本模块直接相关的代码上下文：控制器、服务、Mapper、页面、组件、接口封装、路由、配置、定时任务、消息消费、统计查询等。

不要把未查看、未验证、无法从当前证据支撑的内容写成事实。

证据强度：

- `confirmed`：来自已查看代码、Git diff、现有需求文档、开发计划或用户明确说明，可直接支撑结论。
- `inferred`：从命名、调用链、目录结构、相邻代码或常见业务模式推断，需要标记推断依据。
- `missing`：当前缺少配置、历史数据、外部系统契约、运行环境、联调结果或业务规则，不能直接下结论。

证据冲突处理：

- 用户明确说明与代码表现冲突时，分别记录“用户说法”和“代码证据”，不要强行合并。
- 需求文档与代码实现冲突时，以冲突本身作为待确认问题或已确认偏差。
- 无法证明实际线上配置、历史数据、外部接口行为时，不得写成已确认。

## 执行流程

先区分新分析/生成、局部更新与仅保存已有成果。仅保存时核对原基线及有效修正，保留内容和证据状态，不重跑完整调研或补写；局部更新只执行受影响步骤。适用的范围与写入确认规则继续有效，已有授权不重复索取。

### 确认流程

本节统一维护两种模式的继续、询问、暂停及写入条件，范围证据采用“模块边界”的识别结果。

写入或更新 `agent-works` 文档前，自行核定下列信息，并在报告适用位置保留依据；它们是范围与写入检查项，不是逐项人工审批清单：

- 本次核查的具体业务模块。
- 本次纳入核查的文件范围：列出业务文件，说明排除的构建产物、临时文件或无关文件。
- 识别出的业务功能：中文标题、对应文件和拆分理由；输出目录按全局规则确定，不为每个功能另设无消费方的目录名。
- 已找到的需求、开发计划或已有 `business-audit.md` / `development-trace.md` 文档。
- 输出动作：标明是新建文档还是更新已有文档，以及目标路径。

按以下条件从上到下匹配，决定下一动作：

| 条件 | 动作 |
| --- | --- |
| 核查对象无法确定，或多个候选会实质改变边界与结论；拟扩大范围、覆盖对象归属不明或写入超出已有授权 | 先完成独立调研，展示具体候选、证据、差异和推荐；仅确认尚未解决的决定，暂停依赖部分，其他工作继续 |
| 范围可确定，且只要求核查、讨论或给结论，未要求保存 | 按已定位范围对话交付，不创建或修改报告；不因模块名缺失或来自分析而阻塞 |
| 已要求生成、保存或更新报告，目标范围能由用户指向、会话及项目证据确定 | 按指定路径、已有同范围报告或全局目录规则直接写入；常规标题、功能拆分及文件归属自行确定并说明依据，不要求用户再确认模块名或目录名 |

业务规则或运行证据尚未明确时，可以在已授权报告中保留待确认问题与盲区，不因结论不完整而要求批准全部文件。没有答复不视为同意；已有有效授权直接复用，新增信息仅在实质改变范围、对象或写入风险时触发补充确认。

### 执行流程

1. 判断用户意图：快速核查还是正式产档。
2. 定位项目根目录，查看 `git status --short` 获取当前改动范围。
3. 结合会话上下文确认本次需要核查的业务文件，排除构建产物、依赖目录、临时文件和无关文档。
4. 按“模块边界”识别模块及业务链路，按“确认流程”处理需要决定的缺口。
5. 查找与该模块相关的需求、开发计划、已有 `agent-works` 文档和关键代码上下文。
6. 从改动代码反推本次触达的业务功能，并按“业务功能拆分规则”分组。
7. 围绕每个业务功能构建完整业务链路：入口、核心处理、状态流转、异常分支、对外输出、上下游影响、补偿与运营落地。
8. 结合 `references/audit-dimensions.md` 逐项核查合理性和遗漏风险，并标明证据强度。
9. 快速核查模式：直接输出初步业务风险结论、已确认问题、待确认问题、无法确认风险和建议下一步。
10. 正式产档模式：按“确认流程”核定范围、证据和写入对象，满足写入条件后生成或更新 `business-audit.md`。
11. 完成后汇报生成或更新的文档路径、覆盖的业务功能、主要证据来源、结论摘要和剩余盲区。

## 核心约束

### 核查原则

1. 以用户指定或项目证据支持的本次改动范围为边界，标明识别依据，推断和待核实部分不冒充用户确认。
2. 以“本次开发触达的业务功能”作为核查单位，而不是按文件逐个点评。
3. 问题必须绑定完整业务链路中的位置和影响，不能只给局部代码意见。
4. 结论按下述“问题分类与严重级别”区分已确认、待业务确认及暂无法确认的问题。
5. 纯代码缺陷只能作为业务影响的证据，不作为输出主体。

### 问题分类与严重级别

问题类别与 [信息来源中的证据强度](#信息来源) 分开标记：

| 类别 | 判断与证据要求 |
| --- | --- |
| 已确认问题 | 有明确代码证据与业务影响，能判断存在风险或遗漏；通常必须具备 `confirmed` 证据。 |
| 待业务确认问题 | 代码存在疑点，是否构成问题取决于业务规则、外部契约或部署约束；可使用 `confirmed` 或 `inferred`，写清待确认规则。 |
| 暂无法确认的风险点 | 当前证据不足，通常对应 `missing`；说明需要补充的上下文、数据、配置、联调或运行环境材料。 |

不能把 `inferred` 或 `missing` 写成已发生事实。严重级别用于表达影响，不能代替证据强度：

- `high`：会直接造成业务闭环断裂、关键状态错误、数据严重不一致、权限失控或上线后高概率出问题。
- `medium`：存在明显遗漏或兼容性风险，但需特定条件才会暴露，或影响范围相对可控。
- `low`：问题局部、影响轻微，或更多属于完整性改进项。

### 业务功能拆分规则

从改动代码反推业务功能时，优先按业务目标拆分，而不是按文件拆分。

拆分优先级：

1. 用户或需求文档明确列出的验收项、功能点、流程节点。
2. 独立业务目标，例如新增隐患、整改闭环、复查确认、统计看板。
3. 独立状态闭环，例如提交、派发、整改、验收、关闭。
4. 独立用户入口或外部入口，例如页面操作、接口调用、导入、定时任务、消息消费。
5. 独立下游影响，例如待办、消息、统计、导出、第三方同步。

合并规则：

- 多个文件共同完成同一个业务目标时，合并为一个业务功能。
- 同一接口同时影响主流程和统计/消息等旁路输出时，主流程作为核心功能，旁路输出作为该功能的链路环节。
- 如果两个功能有独立入口、独立状态闭环或独立上线验收标准，应拆分。

### 报告接入

正式产档前完整读取 [固定报告模板](references/report-template.md)，其唯一维护目录、问题字段、填写与内容验收。快速核查沿用已声明的对话模式，不自动生成正式文件；保存和局部更新保留授权基线。

### 输出约束

- 文档内容使用中文。
- 快速核查与正式报告均说明模块和范围来自用户指定、项目证据识别还是待核实，只有实质未决才要求进一步确认。
- 不复制敏感配置值；涉及配置时只写文件位置、用途和环境差异。
- 不夸大结果，不把推测写成事实。
- 未执行的验证、测试、联调或线上行为，不得写成“已确认”。
- 当未发现明显问题时，也要写清剩余盲区和未覆盖范围。
- 本技能不替代代码 review；如发现纯代码缺陷，可作为业务影响的补充证据，而不是输出主体。
- 本技能不审查页面排版、颜色、动画、风格统一、DESIGN 遵循或前端复用治理；页面体验交给 `frontend-ux-audit`，DESIGN 合规交给 `design-compliance-audit`，前端重复实现和抽象边界交给 `frontend-reuse-governance`。

## 产出边界与交付

正式核查文档记录本次改动的业务闭环结论、证据、风险和处理状态；完整需求、实施过程和模块架构由对应文档维护。快速核查仅在现有范围说明中表达边界，不因此落盘。

### 输出位置与命名

- 输出目录遵循全局协作规则 `~/ai-agent-config/config/force/collaboration-rule.md` 的“建文档目录时”；本技能文件名为 `business-audit.md`。
- 文档标题使用中文业务功能名称。
- 如果目标 `business-audit.md` 已存在，优先更新已有文件；更新时保留仍然准确的历史内容，删除或改写过期内容。
- 不为同一功能创建多个同类核查文档。

## 验证与完成标准

逐功能检查入口、状态、权限、上下游和异常补偿的证据链；confirmed、inferred、missing 分别有依据。快速核查不落盘，正式产档有写入授权、可追溯范围及适用的未决状态，不把证据识别冒充用户确认；报告未执行验证与剩余盲区，不将代码审查代替业务闭环结论。按问题走读证据→触发→影响→处理→复验，检查问题标识、分类和证据强度一致，汇总不重复定义详情；未解决、已解决与待复验状态须有相应证据，建议不等于已实施。

正式报告或整体重构后运行 `python3 <skills-root>/skill-authoring-standard/scripts/validate_document_template.py <产物路径> --template <本技能目录>/references/report-template.md`；字段内容按同一模板核对，保存和局部更新不借格式检查重排全文。
