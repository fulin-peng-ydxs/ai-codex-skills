# 模块架构文档输出契约

## 适用规则

新建、重构或系统性优化模块架构文档时，默认遵守本契约。用户明确指定其它结构，或仓库已有必须保持的文档模板、发布规范或机器读取契约时，可以偏离；偏离项和原因必须在交付说明中列出。

标题语言跟随文档语言。中文使用下述固定标题；用户明确要求英文时使用文末对应标题。除上述例外外，不修改固定 Markdown 二级章节名称和顺序，不新增其它 Markdown 二级章节。模块特有内容进入语义最接近的固定章节，使用三级或更深标题。

## 固定章节与顺序

一级标题使用模块名称。以下十个 Markdown 二级章节必须全部保留、非空并按固定顺序出现：

```markdown
# {模块名称}模块架构

## 文档范围与结论摘要
## 模块定位与职责边界
## 核心技术与实现机制
## 架构组成与调用关系
## 使用与运行方式
## 核心流程与状态变化
## 数据、权限与配置
## 上下游依赖与影响范围
## 验证与测试入口
## 风险、限制与待确认项
```

某章不适用于目标模块时，保留章节并写明“不适用”、判断依据和对模块理解或运行是否有影响。证据不足时写“当前证据未发现”或“待确认”，说明已检查的入口；不得静默删除章节，也不得用常见框架行为补全事实。

## 各章最低内容

### 文档范围与结论摘要

至少说明：

- 模块名称、所属系统、代码范围和明确排除范围；
- 文档面向的开发、运维、产品或使用角色；
- 一段可以脱离后文阅读的当前架构结论；
- 事实和验证截止点，区分静态确认、实际执行与待确认。

### 模块定位与职责边界

至少说明模块解决的问题、主要调用者或使用者、负责事项、不负责事项、核心输入和输出。边界必须结合用户入口、API/CLI、数据所有权、运行单元或平台能力，不能只根据目录名判断。

### 核心技术与实现机制

至少解释关键代码入口、主要机制和选择该机制后形成的运行约束。按事实覆盖算法、框架机制、状态机、任务、缓存、并发、事务、扩展点、错误处理或性能容量；每个关键结论应关联路径、类、函数、配置、表或测试证据。

### 架构组成与调用关系

至少给出组成单元、职责和调用方向。推荐使用稳定表格：

| 组成单元 | 职责 | 主要入口 | 调用或数据方向 | 证据 |
|---|---|---|---|---|

存在三个以上组成单元、分支调用、异步任务或外部系统时使用一张必要的 Mermaid 图；简单线性模块使用表格或短步骤，不为满足格式强行画图。本章重点解释模块内部组成和主调用路径；跨模块的构建、运行、数据和配置依赖在 `上下游依赖与影响范围` 中展开，避免重复。

### 使用与运行方式

面向真实使用者或调用者，至少说明入口、前置条件、操作或调用方法、成功结果和失败反馈。根据模块事实使用 `architecture-doc-model.md` 中的页面、API/SDK/CLI、运维或开发接入三级标题。没有直接用户入口时，说明由哪个上游模块、任务或代码接口消费。

### 核心流程与状态变化

至少还原一条最能解释模块价值的真实主流程，连接入口、核心处理、数据或状态变化、下游输出和失败路径。存在状态机时使用状态迁移表；存在异步、重试、回退或补偿时必须说明触发和终止条件。简单库模块可写调用与返回链路，但不能省略本章。

### 数据、权限与配置

按事实说明：

- 数据表、文件、缓存、消息、主要字段或其它数据结构及所有权；
- 功能、操作、行级、租户、资源归属、审计或敏感数据权限；
- 配置文件、配置键、环境变量、默认值、外部资源和生效方式。

没有持久化、权限模型或运行配置时，分别写明不适用及代码依据，不能把前端显隐、调用约定或默认框架行为推断为真实权限和配置机制。

### 上下游依赖与影响范围

至少列出模块边界之外的上游输入、下游输出、共享能力、外部系统和变更影响，并区分构建依赖、运行调用、数据依赖和配置依赖。推荐使用：

| 关系方 | 关系类型 | 输入或输出 | 失败影响 | 变更兼容要求 | 证据 |
|---|---|---|---|---|---|

没有独立下游时仍说明模块如何被消费；共享数据库、公共包、配置中心和生成代码必须写清所有权及影响范围。

### 验证与测试入口

列出与模块直接相关的单元、集成、契约、端到端、扫描、CI 或手工验收入口，说明覆盖目标和运行条件。命令、测试结果和页面行为必须区分：

- `已执行`：本次实际运行并获得成功结果；
- `静态确认`：从脚本、配置或测试源码确认存在，但本次未执行；
- `待确认`：当前证据不足或依赖不可访问。

没有模块测试时保留章节，写明检查范围、缺口和风险，不编造测试命令或覆盖结论。

### 风险、限制与待确认项

使用稳定表格：

| 类型 | 事项 | 证据状态 | 影响 | 建议或验证方式 |
|---|---|---|---|---|

类型至少区分实现风险、数据/权限风险、依赖风险、已知限制和证据缺口。证据状态使用 `已确认`、`推断`、`缺失`；没有发现明确风险时，说明检查范围和剩余证据边界，不写“绝对无风险”。

## 内容归属规则

| 内容 | 固定归属 |
|---|---|
| 页面、API、SDK、CLI、任务和运维入口 | `使用与运行方式` |
| 数据模型、权限、安全和配置 | `数据、权限与配置` |
| 性能、容量、缓存、并发和扩展机制 | `核心技术与实现机制` |
| 兼容性、外部系统、共享包和变更影响 | `上下游依赖与影响范围` |
| 测试、扫描、CI、截图和人工验收 | `验证与测试入口` |
| 当前问题、限制、推断和证据缺口 | `风险、限制与待确认项` |

同一事实只在固定归属章节完整说明，其它位置使用链接或一句话引用，不另建同义 Markdown 二级章节。

## 更新已有文档

- 保留仍与当前代码、配置和权威文档一致的有效事实，将其迁移到固定信息归属；不能为了套骨架删除模块特有机制、接口、数据、权限或风险。
- 旧标题与固定章节语义相同则统一为固定标题；项目特有标题降为对应章节下的三级标题。
- 合并重复内容，删除历史流水、旧计划、无证据推测、过期路径和来源项目残留。
- 更新前后检查同模块文档、README、AGENTS 和架构索引中的链接与锚点，必要时同步修复。
- 多模块批量生成时，每篇文档都独立满足本契约，不把某模块缺失章节借由总索引代替。

## 英文章节标题

英文文档使用以下对应标题并保持相同顺序：

| 中文 | 英文 |
|---|---|
| 文档范围与结论摘要 | Document Scope and Summary |
| 模块定位与职责边界 | Module Purpose and Responsibility Boundaries |
| 核心技术与实现机制 | Core Technologies and Implementation Mechanisms |
| 架构组成与调用关系 | Architecture Components and Call Relationships |
| 使用与运行方式 | Usage and Runtime Operations |
| 核心流程与状态变化 | Core Flows and State Changes |
| 数据、权限与配置 | Data, Permissions, and Configuration |
| 上下游依赖与影响范围 | Upstream and Downstream Dependencies |
| 验证与测试入口 | Verification and Test Entry Points |
| 风险、限制与待确认项 | Risks, Limitations, and Open Questions |

英文一级标题使用 `# {Module Name} Module Architecture`。

## 交付门禁

落地前必须确认：

- 十个固定章节完整、非空、无重复且顺序正确；
- 每章满足最低内容，条件内容位于固定归属下；
- 不适用、静态确认、已执行和待确认没有混写；
- 路径、API、表、配置、测试和依赖方向均已回查；
- Mermaid、表格、链接及被标题调整影响的仓库内锚点有效；
- 已运行 `scripts/validate_architecture_doc_structure.py <document-path>` 并通过；存在已说明的用户或仓库结构例外时使用 `--custom-structure`。
