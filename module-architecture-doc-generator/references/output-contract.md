# 模块架构文档输出契约

产出文档的用途、内容归属与维护入口按 [文档边界声明与审查](~/ai-agent-config/config/force/document-boundaries.md) 表达；已有职责或范围章节承载时，不重复加章。

## 适用规则

结构策略为**参考结构**，按 [模板与结构选择](~/ai-agent-config/config/force/document-output.md#模板与结构选择) 组织及维护已有成果。最低内容、证据状态及必要固定项见下文；章节可适配不等于条目字段或证据要求可省略。

## 参考章节与顺序

一级标题使用模块名称。按能力或运行链路组织正文；以下为阅读骨架，下文主题用于检查内容覆盖，不要求各自成章：

```markdown
# {模块名称}模块架构

## 文档范围与结论摘要
## 模块全景与共享机制
## 能力与运行链路
### {能力或运行链路名称}
## 验证与维护入口
```

不适用主题可省略；影响模块理解、运行或风险判断时说明依据。证据不足须标为待确认并说明已检查的入口，不得以省略掩盖缺口或用常见框架行为补全事实。

## 组织单元与内容分工

遵循 [面向读者的组织与审阅](~/ai-agent-config/config/force/document-output.md#面向读者的组织与审阅)。模块全景承载职责、组成与调用方向；跨能力共用的数据模型、权限、配置优先级和外部依赖在共享机制中完整说明。

每个能力或运行链路按“从哪里使用、怎样处理、得到什么结果、失败如何定位”展开：入口与前置配置、操作或调用、核心机制及代码证据、状态/字段变化和下游交接、权限与兼容边界、成功判据及失败排查。局部风险与证据缺口紧随对应机制，写明证据状态、影响及建议；适用下列主题的字段全部保留，不拆为多套重复清单。

验证与维护入口集中放跨能力测试、运行条件、共用运维路径和未决索引；条目专属测试及结果放在条目旁。风险索引只汇总等级、影响和正文位置，不复制风险解释。单能力模块可合并全景与链路，但仍保留调用者、数据所有权和失败边界。

## 各主题最低内容

### 文档范围与结论摘要

至少说明：

- 模块名称、所属系统、代码范围和明确排除范围；
- 文档面向的开发、运维、产品或使用角色；
- 一段可以脱离后文阅读的当前架构结论；
- 事实和验证截止点，区分静态确认、实际执行与待确认。

### 模块定位与职责边界

至少说明模块解决的问题、主要调用者或使用者、负责事项、不负责事项、核心输入和输出。边界必须结合用户入口、API/CLI、数据所有权、运行单元或平台能力，不能只根据目录名判断。

### 核心技术与实现机制

至少解释关键代码入口、主要机制和选择该机制后形成的运行约束。按事实覆盖算法、框架机制、状态机、任务、缓存、并发、事务、扩展点、错误处理或性能容量；每个关键结论应关联路径、类、函数、配置、表或测试证据。

### 架构组成与调用关系

至少给出组成单元、业务用途、职责和调用方向；首次出现的项目术语或技术名解释其在本系统的作用。区分逻辑分层与实际运行单元，说明关键输入输出、运行位置和生命周期，避免把框架、镜像、容器和任务都称为“服务”。推荐使用稳定表格：

| 组成单元 | 职责 | 主要入口 | 调用或数据方向 | 证据 |
|---|---|---|---|---|

存在三个以上组成单元、分支调用、异步任务或外部系统时使用一张必要的 Mermaid 图；简单线性模块使用表格或短步骤，不为满足格式强行画图。组成图解释模块内部主调用路径；跨模块依赖按下述关系字段放入所属链路，共享依赖放入共享机制。

### 使用与运行方式

面向真实使用者或调用者，至少说明入口、前置条件、操作或调用方法、成功结果和失败反馈。按 `architecture-doc-model.md` 检查适用的页面、API/SDK/CLI、运维或开发接入内容，放入对应运行链路；复杂主题可独立展开，不强制增加同名三级标题。没有直接用户入口时，说明由哪个上游模块、任务或代码接口消费。

### 核心流程与状态变化

至少还原一条最能解释模块价值的真实主流程，连接入口、核心处理、数据或状态变化、下游输出和失败路径。存在状态机时使用状态迁移表；存在异步、重试、回退或补偿时必须说明触发和终止条件。简单库模块可写调用与返回链路，可与实现机制合并说明。

### 数据、权限与配置

按事实说明：

- 数据表、文件、缓存、消息、主要字段或其它数据结构及所有权；
- 功能、操作、行级、租户、资源归属、审计或敏感数据权限；
- 配置文件、配置键、环境变量、默认值、外部资源和生效方式。

没有持久化、权限模型或运行配置时，分别写明不适用及代码依据，不能把前端显隐、调用约定或默认框架行为推断为真实权限和配置机制。

### 上下游依赖与影响范围

至少列出模块边界之外的上游输入、下游输出、共享能力、外部系统和变更影响，并区分构建依赖、运行调用、数据依赖和配置依赖。推荐使用：

| 关系方 | 关系类型 | 输入或输出 | 失败影响 | 变更兼容要求 | 证据 |
|---|---|---|---|---|---|

没有独立下游时仍说明模块如何被消费；共享数据库、公共包、配置中心和生成代码必须写清所有权及影响范围。

### 验证与测试入口

列出与模块直接相关的单元、集成、契约、端到端、扫描、CI 或手工验收入口，说明覆盖目标和运行条件。命令、测试结果和页面行为必须区分：

- `已执行`：本次实际运行，另记通过或失败、环境和结果依据；执行过不等于通过；
- `静态确认（未验证运行行为）`：从脚本、配置或测试源码确认存在，但本次未执行；
- `待确认`：当前证据不足或依赖不可访问。

没有模块测试时仍写明检查范围、缺口和风险，可与验证说明合并，不编造测试命令或覆盖结论。

### 风险、限制与待确认项

使用稳定表格：

| 类型 | 事项 | 证据状态 | 影响 | 建议或验证方式 |
|---|---|---|---|---|

类型至少区分实现风险、数据/权限风险、依赖风险、已知限制和证据缺口。证据状态使用 `已确认`、`推断`、`缺失`；没有发现明确风险时，说明检查范围和剩余证据边界，不写“绝对无风险”。

## 更新已有文档

- 保留仍与当前代码、配置和权威文档一致的有效事实；不能为了套骨架删除模块特有机制、接口、数据、权限或风险。
- 局部更新沿用原有标题和层级；重构时按阅读顺序组织，避免重复定义。
- 合并重复内容，删除历史流水、旧计划、无证据推测、过期路径和来源项目残留。
- 更新前后检查同模块文档、README、AGENTS 和架构索引中的链接与锚点，必要时同步修复。
- 多模块批量生成时，每篇文档都独立满足本契约，不把某模块缺失章节借由总索引代替。

## 英文章节标题

英文文档可使用以下主题名称；这些是最低内容的术语对照，不要求分别成章：

| 中文 | 英文 |
|---|---|
| 文档范围与结论摘要 | Document Scope and Summary |
| 模块定位与职责边界 | Module Purpose and Responsibility Boundaries |
| 核心技术与实现机制 | Core Technologies and Implementation Mechanisms |
| 架构组成与调用关系 | Architecture Components and Call Relationships |
| 使用与运行方式 | Usage and Runtime Operations |
| 核心流程与状态变化 | Core Flows and State Changes |
| 数据、权限与配置 | Data, Permissions, and Configuration |
| 上下游依赖与影响范围 | Upstream and Downstream Dependencies |
| 验证与测试入口 | Verification and Test Entry Points |
| 风险、限制与待确认项 | Risks, Limitations, and Open Questions |

英文一级标题使用 `# {Module Name} Module Architecture`。

## 交付门禁

落地前必须确认：

- 适用的最低内容完整，章节组织清晰、无重复或占位内容；
- 不适用、静态确认、已执行和待确认没有混写；
- 路径、API、表、配置、测试和依赖方向均已回查；
- Mermaid、表格、链接及被标题调整影响的仓库内锚点有效；
- 已运行 `scripts/validate_architecture_doc_structure.py <document-path> --custom-structure` 并通过；默认使用 `--custom-structure`。仅明确采用脚本内置骨架时省略该参数；外部固定契约单独核对。脚本只验证结构，最低内容必须语义复核。
