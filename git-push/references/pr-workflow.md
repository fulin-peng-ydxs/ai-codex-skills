# PR 推送闭环

PR 模式才读取本专题；普通/显式调用、范围及提交消息规则见 [git-push](../SKILL.md)。所有平台写入沿用用户已有授权，不自动改变审批、必需检查或仓库设置。

## 只读预检

首次 PR 写入前核实目标及源仓库、默认/目标分支、当前账号、API 能力和合并方式。工具优先级沿技能正文；连接器具备等价能力时使用连接器。GitHub CLI 路径在技能目录执行以下示例，参数替换为实际核实值：

```bash
python3 scripts/github_pr.py preflight OWNER/REPO --base TARGET
```

脚本只执行帮助探测和 GET：分别读取传统 `branches/<base>/protection` 与 `rules/branches/<base>`，列出审批要求、普通 merge/自动合并开关和源仓库推送权限。fork 源仓库不同则传 `--source-repository OWNER/FORK`，GitHub Enterprise 可传 `--hostname HOST`。API 返回的权限不等于已实际测试 PR 写入；未知、403、含义不明的 404 均保留未核实，不能当作没有保护。只有明确的 `Branch not protected` 才判传统保护不存在。

缺少 CLI、未登录、缺推送权限、合并方式不支持分别报告。SSH 只证明 Git 传输通道，API 登录另行核验；登录通过工具原生入口，不索取聊天中的令牌。可以继续不依赖该条件的本地工作或创建可审阅结果，不直推目标分支、不擅自改变合并方式或规则。需要审核时一次说明实际仓库要求、审批账号限制和平台操作；对话中的“已批准”不能代替 GitHub 审核记录。

## 先准备分支再提交

1. 首次发起先记录原分支、原 HEAD、原分支 upstream 及远端 SHA、PR 源/目标身份，以及已审阅的本地领先提交。远端默认分支只在没有用户/项目约定时作为 PR 目标，返回分支仍同步自己的 upstream；无可信 upstream、detached HEAD 或无法隔离无关提交时只暂停依赖操作。
2. 在任何本地提交前创建并切换到独立工作分支，默认 `codex/` 前缀。原分支的保护 SHA 是建分支前的 HEAD，提交只推进工作分支。Git 原生切换不能安全保留 staged、未提交和未跟踪内容时停止，不 stash 或丢弃。用户明确复用已有源分支时遵从，标记为用户所有、不自动删除；下方 `finish_pr.py` 仅用于返回分支与本次专用工作分支不同的收尾。
3. 同一 PR 的恢复/失败修复使用原记录和原工作分支；不从 `main` 再提交、不新建替代源分支、不重新猜返回分支。确已删除且可验证远端同一源身份时才恢复同名分支，不能覆盖别人的分支。

记录放在 `git rev-parse --path-format=absolute --git-common-dir` 所指目录内的 `codex/pr-push/`。PR 编号未知时可用目标仓库标识与工作分支标识组成稳定文件名，已有 `<仓库>-<PR编号>.json` 继续沿用。准备阶段使用 `version=1, phase=preparing`，`context` 先保存返回分支、upstream、保护 SHA、工作分支、目标远端引用和允许提交清单；提交并正常推送、核实远端 SHA 后补 `source_sha`，创建/复用 PR 后补 `pr_url`。不得写入凭据或业务数据。返回身份及保护 SHA 始终不变；收尾字段示例见下方。

## 推送、PR 与真实修复轮次

正常推送已核定源分支并核对源 SHA，不直推目标分支。按目标仓库/分支和源仓库/分支查找开放 PR，唯一匹配则复用；结果不明先查询，避免重复创建。完整差异和所有待合入提交都须属于授权范围，无差异不创建空 PR。

标题、正文按仓库模板维护。对本次自行创建的 PR，获准范围变化或失败修复后更新标题/正文以反映最终实现和实际验证；他人的描述、目标分支、草稿状态、评审人不擅自修改。结构化参数优先；CLI 多行正文使用本次专用临时文件与 `--body-file`，调用后回收。

默认普通 merge、自动合并，不使用 squash/rebase、管理员绕过、强推、自动审批或修改仓库规则。核实平台允许普通 merge 后使用：

```bash
gh pr merge PR_URL --auto --merge --match-head-commit VERIFIED_SOURCE_SHA
```

可能立即合并，仍须查实际状态、源 SHA、合并时间和提交。明确禁止自动合并或只要求创建时遵从；普通 merge 不可用或权限不足时保留 PR 并报告，不静默改用 squash/rebase。普通 merge 可用而自动合并未启用时，不改变仓库开关；用户已授权完成合并则可在同一预算内等到平台条件满足后执行普通 merge。用户只要求创建或明确限制执行方式时遵从。

CI 失败先通过 [诊断脚本](../scripts/github_pr.py) 取证，再决定修复或重跑：

```bash
python3 scripts/github_pr.py diagnose PR_URL --expected-head VERIFIED_SOURCE_SHA
```

脚本关联检查名、源 SHA、app、事件、run ID、attempt 和当前/失败步骤，区分规划、依赖安装、真实执行及汇总；不自动重跑，不下载整份日志。同名检查不能视为同一次运行，共用 dashboard URL 也不是唯一身份；名称、链接和来源仍有歧义时保持未核实，不选择一个成功项覆盖失败。新 run 成功不能假定已经替代旧失败；源 SHA 不符、证据不完整保持未核实。需要日志时只读取阻塞项的相关片段。计划或检查绑定有缺陷时先确认根因和改动授权，不能盲目多跑一轮完整 CI，也不能制造空提交、删除失败记录或更改检查状态来促成合并。

修复在同一源分支完成，复核累计差异和新提交后正常推送。远端确认成功后更新 `source_sha`、工作分支预期 SHA、`allowed_commits` 和已授权的验证范围；首次返回分支及其保护 SHA 不变。新一轮等待必须对应真实已审阅且已推送的源码变化，不能将网络重试、换查询方式或同 SHA 重跑视为新轮次。

## 有界等待与完成目标

等待脚本按用户/项目的实际目标选择：

- `--completion merge`（默认）：等待实际合并；即使返回 0，也须分别报告验证状态，不能宣称其余检查都通过。
- `--completion validation --checks-scope all`：用户要求完整 CI/修复验收时，等待实际合并及范围内检查完成。`all` 指该 PR 源提交的检查，不扩展到随后 `main` 的新提交；还可用重复 `--run-id ID` 跟踪已核实的特定运行。原有必需失败不会因另指定 run 而被忽略。

```bash
python3 scripts/watch_pr.py PR_URL --expected-head VERIFIED_SOURCE_SHA --expected-base TARGET --repo REPO_DIRECTORY --state GIT_PRIVATE_STATE --ci-timeout-seconds 1800 --completion validation --checks-scope all --progress
```

预算在第一轮开始时确定并保存。已知仓库 CI job 限时则预留排队和汇总时间：当前脚本采用 `max(30分钟, CI限时+5分钟)`，默认资源上限 60 分钟；无可靠耗时来源回退 30 分钟。超过资源上限不自动等待更久，可用 `--max-wait-seconds` 在获准的资源预算内调整。`--timeout-seconds` 表示用户明确的硬期限，优先于推算值并跨真实修复轮次保留；恢复时更小的显式期限可缩短剩余等待，更大的参数不能加时。仍在既定预算内的正常 CI 不因内部 30 分钟阈值重复请求确认。

同一 `--state` 持久保存 deadline、剩余时间、源身份和最新结果；中断、网络重试或重启继续原预算，墙钟回退不能增加额度。明确获准延长才使用 `--extend-seconds`；真实修复并核实新源 SHA 后使用 `--new-round`，旧轮结果保留。仅调整查看或扩大验证目标不重置时间。脚本拒绝静默缩小已保存的检查范围、丢弃 run 或把验证目标改成只等合并；只有用户明确改变目标时才传 `--allow-goal-change`。切换前在 `goal_changes` 保存新旧目标、原源身份、终态和完整旧结果快照，包括已获取的 SHA、run ID、attempt 及失败详情；不随 `latest` 更新覆盖，原预算继续生效。状态文件与本地收尾串行写入，不同时运行监控和清理。

单条网络请求不超过 30 秒且受剩余预算限制，默认每 60 秒查询一次，可按明确需要指定不超过 60 秒的间隔。脚本将 sleep 控制在 60 秒内，宿主每次等待不超过 60 秒。`--progress` 仅在状态、CI 步骤或阻塞变化时输出精简事件；无变化不重复展开快照。可用事件监听替代轮询，但监听仅唤醒，仍须读取真实状态并保持同一预算。

输出分开列出 `merge_status`、`validation_status`、`required_checks_status`、`additional_checks_status`、`cleanup_allowed` 及实际合并证据。必需检查、附加检查及所选验证范围分别核验来源身份；全部显示成功但身份仍有歧义时，对应状态为 `unverified`，不能报告 `passed`，已观察到的失败仍保留。取消、跳过、未执行、未报告和查询失败都不计为验证通过；依赖安装卡住不能称为测试正在执行。只有源/目标身份匹配且取得实际合并提交与时间时，`cleanup_allowed` 才为真。

| 退出码 | 含义与处理 |
| --- | --- |
| `0` | 所选目标已完成；核对 JSON，合并目标完成不自动代表全部验证完成 |
| `1` | 关闭未合并、冲突、草稿、请求修改、源/目标变化或范围内检查失败/取消；先诊断，保留依据 |
| `2` | 工具、查询、状态文件或证据无法核实；连续三次查询失败停止，不能冒充未合并或已通过 |
| `3` | `REVIEW_REQUIRED`，需要真实平台审核；如用户已安排且明确要求等待，可加 `--wait-for-review`，不重置预算 |
| `8` | 预算耗尽，报告当前实际合并及验证状态；自动合并可继续生效，不擅自关闭 PR 或取消设置 |
| `130` | 用户中断，保留状态和现场，不继续写入 |

获准的业务/CI 修复可自主推进；扩大改动范围、缺少外部审批或改变平台设置时只确认新增依赖。已合并而检查尚未完成/失败，仍可在监控退出后安全同步本地，但交付必须保留该验证结论，不能用“合并完成”替代“验收通过”。

## 合并后返回、同步与清理

只在平台实际合并已确认且监控进程已结束后串行执行，顺序为返回最初分支、同步其已核定 upstream、按 PR 目标核验后清理工作分支。平台查询、PR 身份/源/目标核验及 `fetch` 仍由调用方完成；本地脚本不替代这些远端证据，也不访问网络。脚本复核合并提交可从目标远端引用到达，且本轮源提交已在该合并提交中；证据不符时不修改本地分支。

### 收尾记录与阶段

将已核实的闭环上下文写入 `git rev-parse --path-format=absolute --git-common-dir` 返回目录下的 `codex/pr-push/<目标仓库标识>-<PR编号>.json`。沿用预检/建分支时准备的 Git 私有记录，不写项目报告。旧流程仅有收尾记录时仍兼容；首次收尾才新建的记录必须来自可信任务上下文。已有记录只补充已核实的合并证据，不能覆盖成新的 `pending`。示例中的 SHA、时间、URL 和提交列表必须替换为实际核实值：

```json
{
  "version": 1,
  "phase": "pending",
  "context": {
    "pr_url": "https://github.com/OWNER/REPO/pull/123",
    "merged_at": "<平台实际合并时间>",
    "return_branch": "main",
    "return_upstream": "refs/remotes/origin/main",
    "return_sha": "<创建专用工作分支前的返回分支SHA>",
    "work_branch": "codex/task",
    "source_sha": "<最新已推送并核实的源SHA>",
    "target_ref": "refs/remotes/origin/main",
    "merge_sha": "<平台实际合并提交SHA>",
    "allowed_commits": ["<本任务已审阅提交SHA，逐条填写>"]
  }
}
```

监控结束后保留 `watch` 预算与结果；`context` 在收尾期间保持不变，允许提交列表包括首次提交和本轮已审阅的修复提交。原分支不是 PR 目标时，`return_upstream` 仍填写原分支自己的远端引用。收尾脚本原子保存以下进度；同一记录串行执行：

| 阶段 | 恢复判据 |
| --- | --- |
| `pending` | 原分支须等于首次保护 SHA；核验后准备同步 |
| `syncing` | 原分支须仍在已保存的 from/to；先核验最新 upstream，分叉则保持原分支和记录不变。仍在 from 时重算并保存当前合法目标，不能盲目重放旧 to；已在 to 时认可已执行步骤，再按最新合法计划继续 |
| `synced` | 使用 `synced_sha` 保护原分支，不再要求它等于首次 SHA；只补未完成步骤 |
| `cleaning` | 使用 `delete_token`、`delete_dispatched` 和提交后的删除凭证识别尝试；分支已不存在可补齐收尾。已发出删除而同名分支仍存在时，按重建或身份不明保留，不自动重删 |
| `complete` | 重复执行只核验并返回已完成；同名分支被重新创建或原分支后来变化时保留，不再次删除或覆盖 |

### 同步与清理判据

1. 工作区、暂存区及未跟踪文件须干净；当前分支只能是本次返回分支或工作分支。相关分支在其他 worktree 使用、源 SHA 变化、返回分支不匹配当前阶段保护 SHA 时停止，不接纳无关变更。
2. 在切换或移动原分支前检查最新 upstream：相等则无需移动，落后则仅快进；恢复时也先做此检查，不能先重放旧意图再检查。原分支不是 PR 目标且安全领先自身 upstream 时，允许保持领先：upstream 必须是原分支祖先，全部本地领先提交须在 `allowed_commits` 中，并已进入核实的 PR 合并提交。此时不要求本地 HEAD 与 upstream 相等，不把目标 main 强行合入原分支。历史分叉或未审阅的领先提交仍停止，不 reset、rebase 或制造额外 merge commit。
3. 删除依据是本轮源提交已进入 PR 目标，不要求它是当前返回分支的祖先。脚本在 Git 私有目录建立 detached 验证 worktree，其 HEAD 固定为 PR 合并提交；在该 worktree 内使用不带强制选项的 `git branch -d`，并以命令级临时配置忽略源分支原有 upstream，使 Git 按 PR 合并历史判断。原分支及工作分支的持久 upstream 不变。
4. 删除命令保留 Git 原生 worktree 占用检查，并使用 [引用事务钩子](https://git-scm.com/docs/githooks) 在 `prepared` 阶段再次核验源 SHA 和最新 worktree 占用。已有仓库 `reference-transaction` hook 会被调用并保留其拒绝结果，不绕过仓库策略。保护钩子见 [guard_branch_delete.py](../scripts/guard_branch_delete.py)；不退回底层引用强删或使用 `-D`。
5. 删除命令发出前持久保存 `delete_dispatched=true` 及本次 token；事务提交后写入 `deleted-<token>.json` 凭证。已删除而同名分支重建时，无论 SHA 是否相同均保留。若进程在删除与凭证落盘之间中断，且同名分支仍存在，也按结果不明保留。尝试标记不因后续同步或阶段切换而清零，删除身份在入口和清理前统一复核，不能清除标记自动重删。旧版 `cleaning` 记录缺少尝试标记时同样保守处理；需用户明确授权并重新核实当前分支归属后才另行处理，不伪造旧任务完成。
6. 验证 worktree 的位置由 token 固定，恢复可核验后复用；正常完成时用 Git 原生 `worktree remove` 移除，不强制删除。有文件改动、非预期 HEAD、被锁定或身份不符时保留并报告。记录和删除凭证保留为恢复依据；不批量清理其他分支、worktree 或远端引用。

复用本地收尾脚本，传入实际状态文件的绝对路径和仓库目录：

```bash
python3 <本技能目录>/scripts/finish_pr.py --repo <仓库目录> --state <Git私有目录中的收尾记录.json>
```

返回 `0` 及 `status=complete` 后核对精简结果；`sync_mode=ahead` 是允许的安全领先结果。退出码 `2` 表示本地收尾未完成，保留记录和分支并解释原因；`130` 为中断，恢复时先查询 PR、刷新远端引用，再使用同一记录重跑。已完成的记录保留为重复执行依据，后续可按用户授权清理，但不能在失败恢复前删除。

全部完成才报告 PR 推送闭环成功。已合并但同步或清理失败应报告“远端已合并，本地同步/清理未完成”及仍保留的分支。没有实际合并证据时，超时或失败不得提前切回、对齐或清理。已实际合并但验证失败/超时，可以按同一保护完成本地收尾，同时明确验证未完成；不能据此报告全部验收通过。后续沿同一 PR 和原预算恢复，保留失败依据。

维护时运行 `python3 -B -m unittest discover -s <本技能目录>/tests -p 'test_*.py'`；真实 Git 回归覆盖安全领先、同步/删除后中断、重复清理、同 SHA 分支重建、缺失删除凭证、删除前及事务内新增 worktree 占用、源 SHA 变化、原仓库 hook 保留，以及 upstream 分叉时原分支和记录不变。平台合并证据由测试夹具模拟，不将本地回归解释为真实 GitHub CI 验收。
