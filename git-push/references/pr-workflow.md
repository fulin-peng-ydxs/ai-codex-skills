# PR 推送闭环

本专题在选择 PR 推送时读取。共享范围、确认及本地提交流程见 [git-push](../SKILL.md)。PR 是本地提交之后的推送方式，不提供一套独立的“PR commit”。

## 本地提交与工作分支

1. 提交前记录原分支、原 HEAD、原分支 upstream 及其远端提交、PR 目标仓库/分支和本次允许包含的已有提交。PR 目标优先采用用户及项目约定，否则读取远端默认分支；原分支同步自己的已核定 upstream，不擅自把它改为其他分支。原分支无 upstream 时，能从同名远端及任务明确核实则采用，否则仅暂停后续同步准备；detached HEAD 缺少返回分支时先澄清，不猜测。
2. 首次推送先沿共享流程在原分支完成本地提交，再从提交后的 HEAD 创建并切换到本次专用工作分支，未指定时使用 `codex/` 前缀；工作分支与原分支保持不同。例如从 `main` 发起时，`main` 是最终返回分支，实际 PR 工作分支是创建并切换后的 `codex/...`。记录提交后的原分支 SHA 和本次工作分支 SHA，用作同步及清理的状态保护依据。已有本次提交且无新增改动时直接承接，不制造空提交。原分支的全部本地独有提交都将进入 PR，存在无法安全隔离的无关提交时停止依赖操作并报告。
3. 同一 PR 的失败修复或超时恢复优先执行下方 [失败修复与同一 PR 恢复](#失败修复与同一-pr-恢复)，不重新执行首次建分支步骤；继续使用已记录的原本地工作分支及远端源分支。独立任务不复用旧 PR，也不混入旧 PR 未合并的内容。所有分支切换须保护已有暂存、未提交及未跟踪文件；不能安全切换时保留提交并报告，不擅自 stash 或丢弃。

首次发起时在当前任务记录中保留闭环上下文：目标仓库、最初返回分支及其 upstream、首次提交后的返回分支保护 SHA、本次创建的本地工作分支、远端源仓库/分支、PR URL，以及本轮允许的提交范围、本地工作分支 SHA 和已推送且远端核实的源 SHA。失败交付保留这些恢复依据，不另建阶段报告或将凭据写入记录。最初返回分支、upstream 和返回分支保护 SHA 在同一 PR 的后续修复中保持不变；源提交等可变状态仅按恢复步骤更新。上下文缺失或与实际状态冲突时先核实，无法核实时停止相关写操作，不能根据当前检出的工作分支猜测原返回分支。

## 失败修复与同一 PR 恢复

1. 查询已记录 PR 的实际状态、源/目标仓库与分支，并对照闭环上下文；已合并则直接核验合并证据并进入同步清理，不再向已合并 PR 推送；已关闭但未合并时报告，不擅自重新打开或创建替代 PR。仍开放且属于同一任务时继续以下步骤。
2. 在修改或提交修复前确认当前分支就是已记录的原 PR 本地工作分支；当前在 `main` 或其他分支时，安全切换到该工作分支。工作分支仍存在时不得另建修复分支替代；确已删除且可核实原远端源分支时，可恢复相同本地分支名并核对提交，不能覆盖同名的其他工作。恢复过程不改写最初返回分支，也不把当前工作分支登记为新的返回分支。
3. 在该工作分支按已有开发/修复授权修改、验证，并沿共享消息、暂存和提交规则生成修复提交；不在原返回分支再次提交或 cherry-pick 修复。核对累计 PR 差异和新增提交均属于本任务，保留原返回分支的保护 SHA；只有本轮授权产生且已审阅的源分支变更才可更新预期状态，等待期间发现的其他人推送或无关提交不能自动接受为新基线。
4. 正常推送到原远端源分支，保留原 PR URL、目标及源分支身份，不重复建 PR。推送成功并读取远端确认后，将已核实的源 SHA、工作分支保护 SHA 和允许提交范围更新到最新修复提交；例如由 B 更新为 C。推送失败时保留本地修复提交，分别记录本地 C 与仍在远端的 B，不能将 C 冒充已推送提交。
5. 重新查询自动合并设置，按默认规则核验或重新启用；所有 `--match-head-commit`、等待脚本的 `--expected-head`、实际合并核验及最终清理均使用本轮最新且已核实的源 SHA，不能继续使用旧 B。有明确授权继续时，重新推送后开始新一轮有上限的等待；网络重试、查询重启不算修复轮次，不能借此重置当前等待上限或无限修复。
6. 确认本轮最新提交已实际合并后，仍返回首次记录的原分支及 upstream，按下方收尾阶段记录检查并同步，最后清理原 PR 本地工作分支。首次返回分支保护 SHA 不变，但自身已完成的同步使用收尾记录的 `synced_sha`，不能把已同步的 M 再与初始 B 比较。清理资格沿用首次发起的同一闭环，不因恢复而扩大到其他既有分支。任何环节未完成时保留现场及更新后的上下文。

## 推送、PR 与自动合并

正常推送到已核定的远端源分支并核对源 SHA，不直推目标分支。按目标仓库、目标分支和源仓库/源分支查找开放 PR，匹配则复用；多个候选无法判断时报告具体歧义。创建前核对完整 PR 差异及提交范围，无待合入差异时报告无需创建。创建结果不明时先查询再重试，避免重复 PR。

标题和正文遵守仓库模板，以最终改动和实际验证为依据；不擅自修改已有 PR 的正文、目标、草稿状态或评审人。优先传结构化参数；CLI 多行正文使用本次专用临时文件与 `--body-file`，调用结束立即清理，不让 Shell 展开文案。

默认为本次 PR 启用自动合并，合并方式采用保留源提交历史的普通 merge，不默认使用 squash 或 rebase。先核对仓库级允许开关、权限、套餐、合并方式及分支规则；仓库只允许 squash/rebase、要求线性历史或存在其他不允许普通 merge 的约束时保留 PR 并提示，不静默降级或修改仓库规则。用户明确指定其他合并方式时按其要求执行，但仍遵守后续不自动重置及无法快进则报告的边界。GitHub 示例：

```bash
gh pr merge <PR_URL> --auto --merge --match-head-commit <已核对的源SHA>
```

条件已满足时可能立即合并，仍须读取实际合并证据。合并队列遵守其原有规则，不使用管理员绕过。用户要求草稿、不自动合并或仅创建时遵从；仓库未允许自动合并或设置不支持时保留 PR 并提示，不能擅自改仓库设置。存在这种明确阻塞时不进行无意义等待，本次闭环按未完成交付。

## 有时限的合并等待

默认总等待上限 **30 分钟**，轮询间隔 **60 秒**，用户可指定其他上限；一次等待从首次确认合并状态起使用同一个单调时钟截止时间，重试、换查询方式和进程重启不能重置预算，重启脚本须传入剩余秒数。一次网络命令最多 30 秒，且不超过剩余预算。仅需要监测 PR 实际状态和必要检查，不持续下载日志，也不轮询所有历史 workflow。

GitHub CLI 提供 [PR 状态查询](https://cli.github.com/manual/gh_pr_view)、[必需检查查询](https://cli.github.com/manual/gh_pr_checks)；支持且账号可用时可用 [事件监听](https://cli.github.com/manual/gh_event_listen) 降低查询次数。事件仅为唤醒信号，监听开始后和重连后读取快照以覆盖丢事件；仍使用同一个截止时间，不能将监听进程退出或任意单个事件解释为已合并。事件功能不可用时直接使用受控轮询，不把预览功能设为前置条件。

轮询复用脚本，先确认 `gh` 已安装且已登录；可用连接器能覆盖相同能力时可使用它，但也必须保持截止时间、状态核验及最小输出：

```bash
python3 <本技能目录>/scripts/watch_pr.py <PR_URL> --expected-head <已核对的源SHA>
```

脚本只读，默认参数与上述规则一致；通过 `--timeout-seconds`、`--interval-seconds` 调整。命令放在可取消、可短时让出的执行会话中；每次工具等待不超过 60 秒，单次进程在内部查询并判断，只输出最终精简 JSON，不将每次快照送给模型。仅发生阻塞、阶段变化、超时或结束时解释状态，不重复展开相同日志；遵守宿主的必要进度反馈要求。

- 退出码 `0`：PR 为 `MERGED`，源 SHA 匹配，且取得合并时间及合并提交。继续同步清理，不能仅凭退出码跳过 JSON 中的证据核对。
- 退出码 `1`：PR 已关闭但未合并、必需检查失败/取消、冲突、草稿、请求修改或源 SHA 变化。停止等待并报告具体原因和恢复入口。
- 退出码 `2`：查询连续失败 3 次、工具缺失或响应无效，报告无法核实；不能当作未合并或已合并。
- 退出码 `8`：总等待超时，保留当前工作分支、PR 和自动合并设置并报告；后续恢复先查询 PR 最新状态，不能盲目重推或重复建 PR。
- 退出码 `130`：用户中断，停止查询并保留现场。不得把中断解释为完成或继续写操作。

必需检查成功仅代表合并条件之一，不能替代 `MERGED`。失败时保留当前工作分支和 PR，按 [失败修复与同一 PR 恢复](#失败修复与同一-pr-恢复) 承接已有授权；没有修复授权时仅报告，不擅自修改业务代码。权限或网络暂时失败不等于 PR 失败；缺少审批可等待至总上限，明确请求修改则提前报告。

## 合并后返回、同步与清理

只在平台实际合并已确认后执行，顺序为返回最初分支、同步其已核定 upstream、按 PR 目标核验后清理工作分支。平台查询、PR 身份/源/目标核验及 `fetch` 仍由调用方完成；本地脚本不替代这些远端证据，也不访问网络。脚本复核合并提交可从目标远端引用到达，且本轮源提交已在该合并提交中；证据不符时不修改本地分支。

### 收尾记录与阶段

将已核实的闭环上下文写入 `git rev-parse --path-format=absolute --git-common-dir` 返回目录下的 `codex/pr-push/<目标仓库标识>-<PR编号>.json`。它是 Git 本地运行态，不是项目报告，不加入提交；首次进入收尾时创建，恢复时读取同一文件，禁止覆盖成新的 `pending`。示例中的 SHA、时间、URL 和提交列表必须替换为实际核实值：

```json
{
  "version": 1,
  "phase": "pending",
  "context": {
    "pr_url": "https://github.com/OWNER/REPO/pull/123",
    "merged_at": "<平台实际合并时间>",
    "return_branch": "main",
    "return_upstream": "refs/remotes/origin/main",
    "return_sha": "<首次本地提交后的返回分支SHA>",
    "work_branch": "codex/task",
    "source_sha": "<最新已推送并核实的源SHA>",
    "target_ref": "refs/remotes/origin/main",
    "merge_sha": "<平台实际合并提交SHA>",
    "allowed_commits": ["<本任务已审阅提交SHA，逐条填写>"]
  }
}
```

`context` 在收尾期间保持不变，允许提交列表包括首次提交和本轮已审阅的修复提交。原分支不是 PR 目标时，`return_upstream` 仍填写原分支自己的远端引用。收尾脚本原子保存以下进度；同一记录串行执行：

| 阶段 | 恢复判据 |
| --- | --- |
| `pending` | 原分支须等于首次保护 SHA；核验后准备同步 |
| `syncing` | 已先保存 `sync_intent.from/to`；原分支仍在 from 则重试快进，已在 to 则认可本次同步已执行，其他 SHA 停止 |
| `synced` | 使用 `synced_sha` 保护原分支，不再要求它等于首次 SHA；只补未完成步骤 |
| `cleaning` | 同步已完成，继续核验和删除；分支已不存在则认可删除已执行，补齐记录 |
| `complete` | 重复执行只核验并返回已完成；同名分支被重新创建或原分支后来变化时保留，不再次删除或覆盖 |

### 同步与清理判据

1. 工作区、暂存区及未跟踪文件须干净；当前分支只能是本次返回分支或工作分支。相关分支在其他 worktree 使用、源 SHA 变化、返回分支不匹配当前阶段保护 SHA 时停止，不接纳无关变更。
2. 返回原分支后，与自身 upstream 相等则无需移动；原分支落后时仅快进。原分支不是 PR 目标且安全领先自身 upstream 时，允许保持领先：upstream 必须是原分支祖先，全部本地领先提交须在 `allowed_commits` 中，并已进入核实的 PR 合并提交。此时不要求本地 HEAD 与 upstream 相等，不把目标 main 强行合入原分支。历史分叉或未审阅的领先提交仍停止，不 reset、rebase 或制造额外 merge commit。
3. 删除依据是本轮源提交已进入 PR 目标，不要求它是当前返回分支的祖先。仅删除原记录中的本次工作分支，且它仍匹配核实的源 SHA、未被 worktree 使用。脚本先验证 PR 目标中的祖先关系，再使用 `git update-ref -d <工作分支完整引用> <预期源SHA>` 原子比较并删除，防止检查后引用变化被误删；这不是对未合并内容的强制删除。清理仅该分支的本地配置，不改原分支 upstream，不删除远端分支或批量清理其他分支。
4. 同步意图在 Git 写入前保存；执行后记录 `synced_sha`。删除意图同样先保存，实际已删但结果尚未落盘时可从 `cleaning` 恢复。同步与清理失败都保留最后有效记录，不因自身已完成的操作误判为外部修改，也不把后来重新创建的同名分支纳入旧任务。

复用本地收尾脚本，传入实际状态文件的绝对路径和仓库目录：

```bash
python3 <本技能目录>/scripts/finish_pr.py --repo <仓库目录> --state <Git私有目录中的收尾记录.json>
```

返回 `0` 及 `status=complete` 后核对精简结果；`sync_mode=ahead` 是允许的安全领先结果。退出码 `2` 表示本地收尾未完成，保留记录和分支并解释原因；`130` 为中断，恢复时先查询 PR、刷新远端引用，再使用同一记录重跑。已完成的记录保留为重复执行依据，后续可按用户授权清理，但不能在失败恢复前删除。

全部完成才报告 PR 推送闭环成功。已合并但同步或清理失败应报告“远端已合并，本地同步/清理未完成”及仍保留的分支。超时或失败时不提前切回原分支、对齐引用或删除恢复依据；后续沿同一 PR 查询与恢复，不把失败 PR 混入独立任务。

维护时运行 `python3 -B -m unittest discover -s <本技能目录>/tests -p 'test_*.py'`；真实 Git 回归覆盖安全领先、同步后中断、删除后中断、重复清理及状态漂移拒绝。平台合并证据由测试夹具模拟，不将本地回归解释为真实 GitHub CI 验收。
