# Git 提交与推送

## 职责与边界

参考：[确认机制](~/ai-agent-config/config/force/collaboration-rule.md#需要先确认时) · [临时产物](~/ai-agent-config/config/force/collaboration-rule.md#临时产物)。

负责确定提交范围、暂存、提交及已授权的推送；PR 是推送方式，默认采用保留提交历史的普通 merge，包含自动合并、限时等待和成功后的本地快进同步清理。提交消息必须由 [git-commit-message-authoring](../git-commit-message-authoring/SKILL.md) 生成，不在本技能维护消息模板。本文维护 Git 写入顺序、范围保护及调用模式；项目规范维护仓库检查和验证要求。

## 输入与前置条件

核对目标仓库、分支、上游、工作区及已有暂存内容。用户指定文件时只处理指定范围；未指定时根据会话与 diff 选择可可靠归属本任务的改动。保护无关改动及用户原有暂存内容，不把它们混入本次提交；无法安全隔离范围时停止并报告原因。

| 调用方式 | 执行规则 |
| --- | --- |
| 普通请求 | “提交”“推送”“提交并推送”等请求：自行核定范围、消息和暂存结果，不逐步询问。只要求提交就不推送；已要求推送则提交成功后直接推送。无法确定范围时报告具体阻塞。 |
| 显式调用 | 仅 `$git-push` 或明确要求使用本技能，执行下方确认节点。讨论、审查或修改技能不属于调用。 |

### PR 模式与授权

PR 模式默认关闭，仅在用户明确选择 PR 推送或要求创建 PR 时使用；只提交不触发 PR，讨论 PR、仓库设有分支保护或直推被拒绝均不自动开启。普通请求与显式调用的确认规则仍按上表执行，PR 模式不另设一套确认节点。进入 PR 模式先读取 [PR 推送闭环](references/pr-workflow.md)，按其准备上下文及处理恢复。

- “创建 PR”“提交并创建 PR”或“通过 PR 推送”包含本次必要的工作分支推送及 PR 创建授权；“只创建 PR、不推送”仅使用已存在的远端提交，缺少远端分支或提交时报告阻塞。
- PR 推送默认包含启用自动合并、限时等待，以及成功后返回原分支、同步其已核定远端和删除本次本地工作分支，无需另行要求；用户明确限定仅创建、不要自动合并或不要等待时遵从，并说明闭环未完成的部分。该默认行为不授权绕过保护或修改仓库级设置。
- 核对远端平台、工具及登录权限；优先使用能力满足要求的连接器，否则使用对应平台 CLI/API。GitHub CLI 示例为 `gh pr create`、`gh pr view` 和 `gh pr merge --auto`。工具不可用或权限不足时说明受影响步骤，不将 PR 请求静默改为直推目标分支。

### 显式调用的确认节点

仅此模式执行下列节点。每次展示对应范围与依据，已有精确覆盖对应节点的确认直接复用。

| 节点 | 需核定内容 |
| --- | --- |
| 范围 | 展示文件及用途；未指定时提供全部改动、推荐任务范围及自定义选择。多个独立需求让用户选择缩小范围或合并为一次提交。PR 模式同时展示源分支、目标分支及本次包含的已有提交。 |
| 消息 | 调用消息技能后展示文案、对应范围和主要依据，确认后才能暂存。 |
| 暂存 | 展示实际 staged 清单，选择继续本地提交、直接提交并推送或调整。选择直接提交并推送时同时取得两项授权，不再重复确认。 |
| 执行方式 | 暂存节点尚未确定提交方式时，再选择仅提交或提交并推送；推送方式可选普通推送或 PR 推送，未选择 PR 时沿用普通推送，已有明确选择不再询问。若此时选择推送，提交后展示提交摘要并完成最终推送确认；此前已有精确覆盖的推送授权则复用。 |

## 执行流程

1. **确定范围**：读取 `git status`、未暂存及暂存差异，按调用方式核定文件和多需求处理。范围确定后不额外加入文件。首次 PR 推送先记录原分支、原提交、同步目标和本次允许包含的已有提交，不提前切到工作分支；恢复同一 PR 时优先读取原闭环上下文，按专题的恢复步骤切回原 PR 工作分支，不重新认定返回分支。
2. **生成消息**：读取并调用消息技能，传入文件范围、改动摘要、多需求处理决定、用户明确提供的来源与文档、实际验证结果。属于内部调用，不让消息技能重复确认；依赖缺失或不可读时停止提交。
3. **暂存与核对**：完成当前模式适用节点后，按确定路径执行 `git add -- <paths>`。运行 `git diff --cached --name-status` 及必要差异检查，确保内容与范围一致。用户未明确选择全部改动时不使用 `git add -A` 或 `git add .`。
4. **提交**：锁定实际暂存清单及内容；提交前重新核对，发生变化时暂停重新审阅，显式模式取得变更范围确认。锁定后不再添加文件。一次流程生成一条消息并执行一次 commit，不擅自拆分多个提交。
5. **推送**：本地提交完成后再执行所选推送方式。普通推送核对待推送提交和目标后正常 push；首次 PR 推送从已提交的 HEAD 创建并切换到专用工作分支，恢复时直接使用已记录的原 PR 工作分支；按专题执行源分支推送、创建或复用 PR 及默认自动合并。已有提交且无新增改动时跳过消息、暂存和提交，不创建空提交。提交失败不推送；推送失败保留本地提交并报告，不擅自强推、重写共享历史或切换远端。
6. **完成 PR 闭环（仅 PR 模式）**：按专题和 [等待脚本](scripts/watch_pr.py) 限时确认实际合并；平台证据及远端引用核实后，复用 [本地收尾脚本](scripts/finish_pr.py) 返回原分支、同步远端并按 PR 目标核验后清理工作分支。收尾进度保存在 Git 私有元数据中，中断后继续同一记录，不重新初始化。超时、失败、设置不支持或同步清理未完成时交付准确阶段和恢复入口，不将 PR 已创建或自动合并已启用报告为全部完成。

### 提交消息传入与清理

- 优先通过参数或标准输入直接传入提交消息，如 `git commit -m` 或 `git commit -F -`；保持原文与换行，避免 Shell 展开。多行消息本身不构成写临时文件的理由。
- 仅在执行工具要求文件或无法可靠直接传入时创建临时消息文件，路径遵循上述临时产物规则。创建前安排退出清理（如 `trap` 或 `finally`）；提交成功、失败或中断后，在不再读取文件时立即删除本次文件及本次创建且已空的专用目录，不为后续推送或重试保留副本。清理失败时报告具体残留路径与原因，不清理其他任务或用户文件。

## 核心约束

- 构建产物、依赖缓存、锁文件、配置、其他模块、IDE 文件、日志和临时文件不得作为附带改动纳入；用户明确指定的任务文件按其范围核对，敏感内容仍不得泄露。
- 不通过重置、丢弃或擅自 stash 来清理用户改动；不能用只核对文件名代替暂存内容核对。
- 内部调用消息技能不产生新确认流程；普通提交请求不进入上述显式确认节点。
- 已有有效授权持续生效；只提交不等于授权推送，提交成功不等于推送成功。
- PR 模式不使用管理员绕过、强推或修改必需检查来促成合并；不自动审批 PR，也不因创建 PR 获得评论、请求评审或修改仓库设置的授权。
- PR 合并后仅在专题规定的证据及状态保护条件下快进同步；原分支不是 PR 目标时，可保留已审阅且已进入 PR 目标的安全领先提交。工作分支清理以 PR 目标中的合并证据和匹配的源 SHA 为依据，不要求它已合入原分支；有分叉、未审阅领先提交或引用变化时保留，不自动重置、rebase、强删未合并分支或回退已发布历史。

## 产出边界与交付

交付提交标识、实际范围、提交及推送结果、失败位置和保留状态。没有新增改动时核对已有待推送提交，按用户的推送授权处理，不创建空提交。

PR 模式另交付 PR 链接、源/目标分支、自动合并设置、合并提交、原分支同步结果及本地工作分支清理结果。未完成时说明停在哪一步、超时/失败原因和保留分支，并保留专题规定的首次返回分支及最新源提交等恢复上下文；超时后自动合并可能继续生效，须明确提示，不擅自关闭 PR、取消自动合并或删除恢复依据。

## 验证与完成标准

提交前核对范围、内容与授权，提交后核对实际 commit；推送后核对命令结果与远端分支状态。失败明确停在哪一步，保护原工作区和暂存内容，不将部分成功报告为全部完成。

PR 推送完成须有平台实际合并证据、匹配的源提交与远端目标合并提交，以及返回原分支、同步和本次本地工作分支清理的实际结果；用户明确缩小范围时按范围交付。全部必需 CI 已通过不等于 PR 已合并；任一闭环步骤失败须分别报告。低频查询和本地状态判断在受控进程中执行，不将重复快照和完整日志反复送入模型。
